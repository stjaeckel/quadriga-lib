quadriga-lib is a C++ radio channel modelling library with MATLAB / Octave and Python APIs. This document gives the conventions for the MATLAB / Octave wrapper of a C++ function: the MEX file `api_mex/<function_name>.cpp` and its MOxUnit test `tests/mex_tests/test_<function_name>.m`. The C++ function, its documentation block and its Catch2 suite exist first (`md/SPEC_CPP_API.md`); the wrapper converts the arguments, shifts indices, allocates outputs and calls it. It should feel natural to MATLAB users and keep the speed of the C++ library.

These conventions are defaults that keep the wrappers consistent, not rules to satisfy at any cost. Prefer the leaner wrapper; where a convention would make it more complex than the case needs, deviate: a deviation inside the wrapper is made and reported in the hand-over with its reason; one that changes the interface users see (names, argument order, defaults, outputs) is proposed first.

# Interface
- The wrapper takes the names, argument order and defaults of the C++ declaration, so that users learn one interface for all three APIs; the Glossary in `docs_builder/content/api_intro_cpp.md` applies. Where the wrapper differs (an in/out argument split into `x_in` and `x_out`, another output order), its documentation block says how and why.
- Keep the wrapper thin: argument conversion, index shifts, output allocation and the C++ call. Anything that changes results (unit conversions, other defaults, loops over C++ calls) belongs in the C++ library; choosing which C++ function a call maps to, as the multi-frequency mode of `api_mex/interpolate_pattern.cpp` does, is part of the conversion.
- MATLAB indices are 1-based. Indices that are 0-based in C++ are shifted (-1 on input, +1 on output), also inside C++ error messages; indices that are 1-based in C++ (often with 0 = none) pass through, with a comment that no shift is intended. The documentation says "1-based" for every index argument.
- Templated C++ functions are called with `double`, fixed-type functions with their type. Integer outputs keep their C++ type (`arma::u32_vec` is uint32, `arma::uvec` uint64).
- Complex data is one complex array where C++ has an `_re` / `_im` pair, for inputs and outputs, read with `qd_mex_get_complex_Col` / `_Mat` / `_Cube`; real input is accepted as imaginary part 0. A C++ function with an optional `std::complex` output writes it into the output allocated with `qd_mex_init_output`; other results are copied with `qd_mex_copy2matlab(&re, &im)`. The arrayant struct keeps its split fields and `polmat` its real `[8, n]` form. The MEX files use the interleaved complex API (MATLAB R2018a, Octave 8.4 and later). Octave returns a complex result whose imaginary parts are all zero as a real array; tests do not assert `~isreal`.
- Structs carry the names of the C++ members as fields. An arrayant is a 1x1 struct; a multi-frequency arrayant, a `std::vector` of arrayants with one entry per frequency, is a 1xN struct array. A `std::vector` of channels is a 1xN struct array; channel members that hold one entry per snapshot become one array with the snapshot on the last dimension, zero-padded where the number of paths differs. Documentation blocks refer to [[generate_antenna]] and [[hdf5_read_channel]] for the fields instead of repeating them.
- Wrappers and tests run in MATLAB and in Octave.

# Wrapper
- Exemplars: `api_mex/o2i_loss.cpp` (outputs of known size, optional outputs, an index output), `api_mex/mitsuba_xml_file_write.cpp` (no outputs, index inputs, a pass-through index), `api_mex/interpolate_pattern.cpp` (arrayant structs, multi-frequency mode), `api_mex/sos_remove_bias.cpp` (in/out arguments split into `_in` / `_out`, read with `copy = true`), `api_mex/conf_file_read.cpp` (a file reader with struct outputs), `api_mex/gbsm_single_link_channel.cpp` (a channel struct output). Their tests are in `tests/mex_tests/` under the same names. CMake globs `api_mex/*.cpp` when it configures, which `make` does on every run; `cmake --build` alone does not pick up a new file.
- The conversions are in `src/qd_helpers_mex.hpp` and, for structs and `std::any` data, `src/qd_helpers_mex_types.hpp`; logic shared with the Python wrappers (`qd_arrayant_fill_defaults`, `qd_hdf5_select_slots`, ...) is in `src/qd_helpers_wrappers.hpp`; read their comments before writing raw `mx*` code. Struct conversions of the library classes usually live in `src/qd_helpers_mex_types.hpp`, also those that only one section uses, so that they are found in one place; a helper of one MEX file stays `static` in it, so that other MEX files do not parse it, and `api_mex/` holds only the MEX sources. Pass the argument name to every helper that takes one, so that messages name it.
- Traps:
  - The second argument of `qd_mex_get_Col`, `_Mat` and `_Cube` is `bool copy`; a string literal there compiles and means `copy = true`. With `copy = false` the object borrows the MATLAB memory and must not be modified; data that the C++ call changes in place is read with `copy = true`. The same holds for the `copy` argument of `qd_mex_struct2arrayant`, `qd_mex_struct2arrayant_multi` and `qd_mex_struct2channel` (`input, validate, copy, name`).
  - The second argument of `qd_mex_get_string` is the default value, not the name.
  - `qd_mex_get_scalar` returns its third argument for `[]`; the overload without it returns NaN (floating-point types only). A scalar default is therefore given twice: in the `nrhs` guard and as that argument.
  - Index inputs are read with `qd_mex_get_index` or `qd_mex_get_index_Col`, which copy, reject 0 and return 0-based values; a matrix of indices is read as a column and reshaped.
  - `qd_mex_init_output` allocates zeroed MATLAB memory of fixed size that C++ writes into. Its shape must match what C++ produces exactly: another number of elements makes the C++ call fail with "Mat::init(): mismatch between size of auxiliary memory and requested size", the same number in another shape (e.g. `[n_ang, n_out]` for `[n_out, n_ang]`) gives no error and scrambled values; a `std::vector` of cubes that C++ replaces or resizes leaves the MATLAB output zero.
  - The conversion helpers of `qd_helpers_mex.hpp` and `qd_helpers_mex_types.hpp` raise their own MATLAB errors; call them outside `CALL_QD`, which in Octave would catch such an error and repeat the function name in it. Code that throws C++ exceptions, also `qd_snapshot_list` and the helpers of `qd_helpers_wrappers.hpp`, runs inside `CALL_QD`. `make test` checks this (`tests/check_mex_call_qd.sh`); a call that cannot throw may stay outside with the comment `// no CALL_QD: <reason>`.
  - A message built at run time is passed as `mexErrMsgIdAndTxt(id, "%s", msg.c_str())`, never as the format string.
- Check `nrhs` (the upper limit, and the lower one where inputs are mandatory) and `nlhs` first, with `"Wrong number of input arguments."` and `"Wrong number of output arguments."`. All errors use the identifier `quadriga_lib:CPPerror`. The C++ call goes through `CALL_QD(...)`, which passes C++ messages on and makes their `Entry` and `Snapshot` prefixes 1-based.
- An optional input is read as `(nrhs < k) ? default : ...(prhs[k - 1])`, and `[]` gives the default as well. An empty optional array means "not given" to C++. An optional C++ input taken by pointer gets `nullptr` when the argument is omitted or `[]`.
- The first output is set on every successful call, also for `nlhs = 0`, so that a call without assignment shows it as `ans`; further outputs only when requested. An optional C++ output returned in `plhs[k]` gets `(nlhs > k) ? &obj : nullptr` unless it feeds the first output. An output that grows with the data and whose size the wrapper knows is pre-allocated with `qd_mex_init_output`; outputs sized by the call, returned results and small per-element results are copied afterwards.
- A C++ function without results gives a wrapper without outputs: `nlhs > 0` is an error.
- The wrapper is compiled by MSVC for the Windows builds and must load in MATLAB R2024a: the platform rules of `md/SPEC_CPP_API.md`, "Build and platform", apply to it.

# Documentation block
- The rules of the C++ block apply (`md/SPEC_CPP_API.md`, "Documentation block"), with the same one-line summary and the section of the C++ function; do not expand what is brief in C++. A section description (`SECTION_DESC`) of the C++ section has an adapted copy in one wrapper file of the section (e.g. `api_mex/conf_file_read.cpp`, `api_python/qpy_conf_file.cpp`); a change to one goes into the others.
- Differences: the heading is the function name in UPPERCASE; `## Usage:` replaces the declaration, with long calls split by `...` and continuation lines indented by 4 spaces; C++ details (dtype, pointers) are dropped; the type is stated only when it is not `double`; optional inputs state `default: X` instead of the *(optional)* mark (kept only where no default can be stated) and accept `[]`; a C++ return value is listed under `## Outputs:`; outputs are never marked optional; vector outputs state their orientation (`[n, 1]` or `[1, n]`); no links to functions that exist only in another API.
- `make docs` renders the block into `docs/` (commit it with the change); `make` writes the `.m` help file from it. If the wrapper calls a C++ function of another name, also a second one such as a `_multi` variant (overloads of one name need no entry), add the family to `[families]` in `docs_builder/content/api_matching.toml` (`docs_builder/README.md`, "Cross-language buttons").

# Test
- The test checks the wrapper; the physics is pinned by the Catch2 suite. It shows that inputs reach the right C++ argument, outputs come back in their position with the documented size, orientation and class, indices are 1-based in and out, optional inputs work omitted, as `[]` and given, a call with 0 outputs sets `ans` and fewer outputs give the same values, and that wrong argument counts, the wrapper's own checks and one C++ error raise the right message. The shared helpers are exercised by many existing tests: one call with other numeric classes and a transposed vector is enough, no sweeps.
- Exemplar: `tests/mex_tests/test_o2i_loss.m`: one function named like the file, `%%` sections, those that apply, in the order setup, basic call, optional inputs, outputs, other classes (one call), indices, errors, and the local helpers `assert_throws` and `out4` (requests one output more than allowed) after it. Small inputs with results that can be written down, tight tolerances (1e-12 for `double`, a few `single` epsilons scaled by the magnitude with `single` inputs), and code that runs in both MATLAB and Octave (`strfind`, single-quoted strings, no `arguments` blocks). Files are written with distinct names and removed at the end.
- `make` builds and installs the MEX files into `+quadriga_lib/`, `make test` runs all suites. One test runs from MATLAB or Octave with the repository root, `tests/mex_tests` and MOxUnit (`make moxunit-lib` unpacks it into `external/MOxUnit-master/MOxUnit`, then `moxunit_set_path`) on the path, e.g. `test_o2i_loss`. The suite runs in `tests/`, so input files are read as `data/<name>`, and a single test that reads files is started there.

# Hand-over
- The usage line, the test results as actually run (MATLAB, Octave or both), compiler warnings, and every deviation from the C++ interface or from these conventions, with its reason.
