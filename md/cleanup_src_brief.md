# Brief — cleanup of `src/ray_mesh_interact.cpp` (task 1 of 3)

This brief is the whole task description. Read it in full before doing anything, and re-read it at the start of
every phase. Findings go into `md/cleanup_src_report.md` (create it), one section per phase.

## Why

`src/ray_mesh_interact.cpp` (5211 lines) grew through months of physics rounds. It carries the material model, the
interface physics, the slab and stack solver, `ray_mesh_interact` and `ray_state_update`, and the public API
documentation of five functions. About 1230 lines are comment-only; many carry the reasoning of decisions long
taken, how the code used to behave, or measured numbers, rather than what the code does now. `ray_state_update` is one function
of about 2000 lines built from lambdas; `ray_mesh_interact` about 1000. Stephan wants the file to be a clean
foundation before the next project. This is task 1 of three cleanup tasks (then the ray tests, then the
material-model document; `md/acoustic_manager.md` 8).

**Goals (Stephan, 2026-10-20):**

- Remove every stale comment.
- Reduce comments to the necessary minimum without losing readability. **An AI agent that reads only this file must
  understand what it does**: a header overview of the file (what the five public functions do, how the material model,
  the solver and the state machine fit together, the conventions: units, the acoustic mapping, the mass column as the
  acoustic switch), and short comments where the code alone does not say why.
- Improve readability and structure. **One file**, kept as one file, organized in sections (for example: material
  model; interface physics; slab and stack solver; `ray_mesh_interact`; `ray_state_update`). The large functions are
  split into named helper functions with explicit inputs and outputs in place of long lambdas that capture everything.
- Correct scoping: internals in the anonymous namespace, `const` where a value does not change, the narrowest scope
  for every variable, no macros where a constant or an inline function serves (`colocation_dist` is a `#define`
  today).
- Sensible function and variable names: say what a thing is (`dist_orig_fbs`, `nH`, `typeR`, `PLATE_ABS`,
  `MASS_FOLD`, `SHEET_RESOLVE` and the like are candidates; decide in the plan).
- **The public API blocks (`/*!MD … */`) are shortened to the essentials.** They compile into the public
  documentation (`html_docu/cpp_api.html` and its md), so they describe what a user or an AI sees from the
  whole-library perspective: what the function does, its inputs and outputs, units, conventions and limits.
  Internal workings only where a user needs them for context. They must stay correct for what the code does.
- **The tests must not move** (see Hard rules).

## Traps

- The traps of `md/wave.md` 11 and `md/acoustic_manager.md` 9 (run binaries from the repository root, one suite at a
  time, `pkill -f` kills its own shell, `python3 -I`).
- Floating-point order: moving an expression into a helper, hoisting a common factor, or changing `a*b*c` to
  `a*(b*c)` changes the last bits; the rule allows last-digit drift, but a change that moves a near-resonance row (the
  twins' tables, the `Unentered branches … near a pole` case) by more than that is a behavior change.
- `float` and `double`: helpers that take `double` where the code computed in `dtype` change the float template's
  results; keep the precision each value had.
- Lambdas in `ray_state_update` capture per-ray state by reference (the ledger, flags, `next_current`, the hit
  arrays); a split into functions must pass exactly that state, and the order of writes matters (the ledger is
  written at the end of each ray's block).
- OpenMP: the per-ray loop is parallel; helper functions must not introduce shared mutable state.
- The baselines' printed rows come from the tests, not from the library; a library change that leaves every number
  equal leaves them equal.
- Scratch is not kept: the report states every number it relies on.
