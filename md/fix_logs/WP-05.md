## Per item

**B-004.** In the separate-input branch of `geo2cart` and `cart2geo` the local matrices that the flat vectors alias
(`az_a`, `el_a`, `len_a`; `x_a`, `y_a`, `z_a`) are now declared in function scope, as proposed. With B-098 they alias
the caller's arrays when those are F-contiguous float64, otherwise they hold the copies; in both cases they live
until the kernel has run.

**B-005.** Two causes, both in `python_arma_adapter.hpp`:
- `qd_python_anycast` built `arma::Row` / `arma::Col` directly on the numpy buffer for 1-D and `(n, 1)` arrays and
  ignored the strides. It now goes through the general adapter (1-D: a `Row` filled by `qd_python_copy2arma`, 2-D:
  `qd_python_numpy2arma_Mat`, 3-D: `qd_python_numpy2arma_Cube`), which honours strides.
- The general adapter itself (`qd_python_get_shape` / `qd_python_copy2arma`, used by every wrapper) divided byte
  strides by the item size with unsigned arithmetic. That truncates strides that are not a multiple of the item size
  (fields of packed structured arrays: a float64 field has a 12-byte stride, read as 1, so the wrong bytes were
  copied) and turns negative strides into huge unsigned values (the result was right only by 64-bit wrap-around,
  formally undefined pointer arithmetic). New `qd_python_element_strided` returns the array itself when every
  dimension with more than one entry has a non-negative stride that is a multiple of the item size and the data is
  aligned, and otherwise an aligned F-contiguous copy made by numpy. It is applied in `qd_python_copy2arma`,
  `qd_python_get_list_shape`, `qd_python_numpy2arma_vecCube(_Cplx)` and the 4-D parse of `baseband_freq_response`;
  `qd_python_get_shape` now throws (internal error) instead of computing wrong strides if a call site misses it.
  This goes slightly beyond the item (the general adapter, not only the HDF5 writers), because it is the same root
  cause and the B-005 test cases (`x[::-1]`, a structured field) need it.
- The F-contiguity flag of `qd_python_get_shape` is now numpy's `F_CONTIGUOUS` flag. The old stride comparison
  treated a C-ordered `(n, 1)` array (strides 8, 8) as non-contiguous; numpy ignores the stride of a dimension with
  one entry. Only the speed of the copy changes (one `memcpy` instead of the element loop).

**B-035.** When `local_angles` is set, the full `arrayant::interpolate` overload is always called; without `dist`
the projected distance goes into a scratch matrix that is not returned.

**B-036.** Both OpenMP regions (single- and multi-frequency) wrap the loop body in `try` / `catch (...)`; the first
exception is stored as `std::exception_ptr` under a named `omp critical` (`qd_store_first_exception`) and rethrown
after the region, so it keeps its type (`std::invalid_argument` → `ValueError`). The proposed extra validation of
`freq_in` before the region was not added: the C++ function already checks it and the message reaches Python
unchanged; a second check in the wrapper would duplicate the rule. Note: the per-thread buffers (`std::vector` of
`n_freq_in` empty cubes) are allocated inside the parallel region before the `omp for`, outside the `try`; moving them
into the loop body would allocate per snapshot, and a `try` around the `omp for` would deadlock at its barrier. Their
allocation failing is the only remaining way out of the region (vectors of empty cubes, negligible).

**B-096.** `qd_qrt_reader_guard` (declared right after the reader thread) sets a stop flag, notifies the condition
variable and joins the reader with the GIL released, both on the normal path (`reader_guard.join()`, replacing the old
join) and on unwind (destructor). The reader's wait predicate includes the stop flag and returns when it is set. The
guard is destroyed before the slots, mutex and condition variable the reader uses. Repro G-5 and the new test now end
with `MemoryError`. The test is skipped under AddressSanitizer: ASan reserves terabytes of address space at start-up,
so the `RLIMIT_AS` cap cannot make an allocation fail; the normal-module run covers it.

**B-097.** `qd_python_anycast` (now with `qd_python_anycast_array<dtype>`):
- numpy scalars (`numpy.generic`) and 0-d arrays become scalars of their element type (float32 → `float`, int64 →
  `long long`, ...); before they were rejected.
- The element type is chosen by numpy kind and item size (`f8`, `f4`, `i4`, `u4`, `i8`, `u8`) instead of by dtype
  object identity, so pickled arrays, `np.longlong` / `np.ulonglong` and non-native byte order are accepted;
  `py::array_t<T>::ensure` converts byte-swapped data to native order (a copy only then).
- Python `bool`: manager default kept, stored as int64 (reads back as `1` / `0`), now documented. numpy bool, int16,
  float16, complex, 4-D and lists still raise `ValueError: Input '<name>' has an unsupported type.` (not in the
  documented list); pinned by `test_write_dset_unsupported_types`.
- Shapes, the two facts the manager asked for: (1) a 1-element 1-D array reads back as an array of shape `(1,)`, not
  as a scalar (pinned by `test_shapes_round_trip`, entries `v1`, `u1`, also through `hdf5_write_channel(par=...)`).
  Old files: the WP-02 compatibility file `build_linux/scratch/fix/WP-02/compat/old/f2.hdf5` (written by the
  pre-WP-02 library) gives `vec1 ndarray (1,) float64`, `fvec1 (1,) float32`, `u32vec1 (1,) uint32`,
  `uvec1 (1,) uint64`, `row1 (1,)`, `mat11 (1, 1)`, `s_double float`; this is a one-off check, not a pytest case,
  because it needs a 98 KB binary fixture outside `tests/python_tests/`. (2) The `(1, 1)` question: yes, the Python
  writer flattened it. `qd_python_anycast` mapped every 2-D array with one column (`(n, 1)`, also `(1, 1)`) to
  `arma::Col`, which the C++ writer stores as a rank-1 dataset; a C++ `arma::mat(1, 1)` reads back as `(1, 1)`. Fixed
  in the Python layer: every 2-D array becomes an `arma::Mat` (rank-2 dataset), so `(n, 1)` and `(1, 1)` keep their
  shape. 1-D arrays are still stored as vectors (rank 1).
- Speed: the first version copied every array; that made a 1-D 80 MB `hdf5_write_dset` 3.3 times slower than the old
  code (0.036 s → 0.121 s), because the old code aliased the buffer (the B-005 bug). `qd_python_anycast_array` now
  aliases the caller's own F-contiguous array (no byte-order conversion happened) and copies everything else; the
  `std::any` is consumed within the call (`hdf5_write_dset` takes `const std::any *`, `hdf5_write` a
  `const channel *`). Result: 0.0364 / 0.0365 / 0.0364 s new vs 0.0364 / 0.0366 / 0.0367 s old.

**B-098.** Real aliasing (`copy_aux_mem = false, strict = true`), designed so that an alias can only point to memory
that outlives the wrapper call:
- `const py::array_t<dtype> &` (lvalue) overloads alias when the array is F-contiguous and aligned (numpy flags).
- New `py::array_t<dtype> &&` (temporary) overloads always copy (or throw with `strict`): a temporary created in the
  call expression is released before the result is used.
- `py::handle` overloads alias only an object that already is an ndarray of the requested dtype (`isinstance` with
  `PyArray_EquivTypes`, so no conversion); anything they must convert (other dtype or byte order, list, scalar) is
  converted into a temporary and passed to the rvalue overload, i.e. copied.
- Empty arrays are never aliased (an empty object is returned): `arrayant::validate()` and some wrappers resize
  empty members (`element_pos.zeros(...)`, `snap_arma = regspace(...)`), which would throw on a strict alias.
- Deviation from the manager note "alias only the caller's own numpy array": a wrapper parameter declared
  `const py::array_t<dtype> &` that pybind11 had to convert (float32, list, C-order is not converted) is the converted
  array, and it is aliased. This is safe: pybind11 3.0.0 keeps converted arguments in the `argument_loader`
  (`args_converter` in `cpp_function::initialize_generic`, `pybind11.h:401-431`) until the wrapped function has
  returned, and nothing else references that array. Copying it again would add a second copy to every converted
  input. The note's scenario (a temporary released while an Armadillo object still points to it) is what the rvalue
  overload and the `py::handle` overload exclude. The probe shows both views (`conv` = pybind11 converted, `=conv` =
  memptr equals the converted array).
- Probe (`bash build_linux/scratch/fix/WP-05/probe/run.sh`, output `probe/out_final.txt`), memptr == caller's numpy
  pointer for (Col, Mat, Cube, vecCube):

  | Input | `py::handle` | `const array_t &` | temporary | `strict` |
  |---|---|---|---|---|
  | F-order float64, read-only F-order, 1-D float64, 0-d float64 | all True | all True | False (copy) | alias |
  | C-order float64, sliced (non-contiguous), negative strides | all False | all False | False | raises |
  | float32, int64, big-endian `>f8` | all False | all False (aliases pybind11's converted array) | - | raises |

  against the new adapter): `(True, True, True, True)`.

## Behaviour changes for users

- Inputs are no longer copied when they are Fortran-contiguous, aligned arrays of the dtype a function needs (e.g.
  float64 F-order arrays, the arrays returned by the library). The library never writes into them. In
  `get_channels_spherical` batch mode other Python threads must not write into the input arrays during the call
  (they may still remove them from lists or dicts). `arrayant.interpolate(fast_access=True)` and batch mode now really
  read without copying, as documented.
- `tools.geo2cart` / `tools.cart2geo` with separate inputs return correct values for any size (before: wrong values
  above 16 elements, crash for large inputs).
- Arrays with negative strides, byte strides that are not a multiple of the item size (fields of structured arrays)
  or unaligned data are read correctly by every function (before: wrong values for structured fields).
- `hdf5_write_dset` and the `par` data of `hdf5_write_channel`: strided arrays (slices, reversed, columns, struct
  fields) are written with their values (before: wrong data); numpy scalars, 0-d arrays, pickled arrays,
  `np.longlong` and big-endian arrays are accepted (before: "unsupported type"); a Python bool is stored as int64
  (unchanged, now documented); 2-D arrays with one column, including `(1, 1)`, are stored as 2-D datasets and read
  back with their shape (before: stored as vectors, read back as `(n,)`). C++ readers of such files get an
  `arma::Mat` (n×1) instead of an `arma::Col`.
- `hdf5_create_file` returns int64 (before: uint32).
- `arrayant.interpolate(..., local_angles=True)` without `dist=True` returns the local angles (before: uninitialised
  memory).
- `channel.baseband_freq_response` raises `ValueError` for errors inside the parallel loop (e.g. unsorted `freq_in`)
  instead of aborting the interpreter.
- `channel.qrt_file_read` raises `MemoryError` (or the error) when converting fails while the reader thread runs,
  instead of aborting the interpreter.
- New errors (`ValueError`): positions / orientations of `get_channels_planar`, `get_channels_multifreq` and
  single-mode `get_channels_spherical` with more than 3 elements (e.g. `(3, 2)`; before the first column was used
  silently); `channel_export_obj_file` with fewer `interact_coord` columns than `sum(no_interact)` (before zero-padded);
  a 4-D arrayant dict without `center_freq`, or with a scalar `center_freq` for several entries, in `interpolate`,
  `combine_pattern`, `get_channels_multifreq` and `qdant_write` (before: 299792458 or the scalar for every entry); a
  single-frequency arrayant dict whose `center_freq` does not have exactly one element (before: a numpy
  DeprecationWarning for `(1,)`, `RuntimeError` for more).
- Documentation only: kwarg names `sub_cloud_ind` and `map_to_itu` in the docs; dtypes and shapes of `qdant_read`
  layout, `point_inside_mesh`, `generate_speaker` with one frequency, `get_ieee_indoor` `center_frequency` and
  `initial_position`.
