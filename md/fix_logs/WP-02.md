## Per item

The file `src/qd_channel_hdf5.cpp` was rewritten around a small set of helpers (top of the file). Its file format
stays the same, except for the additions listed under B-050.
- `qHDF_id`: owns one HDF5 identifier and closes it in its destructor. No raw `new`/`delete`, no
  `qHDF_close_file` sweep over all objects of the file.
- `qHDF_error_guard`: saves the caller's HDF5 error handler, switches automatic printing off, and restores the handler
  when the function returns or throws.
- `qHDF_dataset`: the checked read helper of B-013. It opens a dataset and checks the rank and every extent (in
  64 bits, overflow-checked) against the expected shape. It checks that the type is numeric and that the file
  actually holds the declared data (see B-013). Only then does the caller allocate. `read()` checks the return code
  and converts to `float`/`double`/`unsigned` through HDF5. It throws `std::invalid_argument` on any failure.
- `qHDF_read_attr`: the checked scalar/vector attribute helper (exists, element count, numeric type, return code).
- `qHDF_read_name`: the checked reader for `Name`.
- Writer helpers `qHDF_create_attr`, `qHDF_write_attr`, `qHDF_write_dset`, `qHDF_write_float`: they check every
  return code and throw `std::runtime_error("HDF5 error: ...")`.

- **B-001.** `hdf5_write` no longer reuses the group of the slot (old `qHDF_get_channel_ID` usage 1). It always
  writes the channel into a new group `/channel_<max+1>` (names that are already taken are skipped). It then
  writes the index and deletes the link to the old group. The old `Data` and `par_*` of the slot are therefore gone,
  as decided. If anything fails while the new group is written, a guard deletes the new group again, and the slot
  keeps its old data. The `par` names and types are validated before the file is touched. With error printing
  switched off only inside the call and every return code checked, a failing `H5Gcreate2`/`H5Dcreate2` now throws.
  Repro `B-003`: `case 1 ...: par fields read back: b=2` and `case 2 ...: x=99`. The script still prints the old
  expectation "a=1 b=2"; `b=2` alone is correct under decision (a).
  - Check of `hdf5_write_dset` (manager's note). The function *adds* a dataset and keeps the rest of the slot: it
    reuses the slot's group and opens or creates `Data`. It does **not** replace an existing dataset: it throws
    "Dataset 'par_x' already exists." This is the documented behaviour (C++, MEX and Python docs, and the MEX test
    "Overwriting dset errors"), so I kept it. The note's "adds or replaces" is wrong on "replaces". New: an invalid
    name or type is rejected before the file is changed, so it no longer reserves an empty slot (tested).
- **B-013.** Every read in `hdf5_read_channel` goes through `qHDF_dataset` / `qHDF_read_attr`. Covered:
  - coefficients, delay (extent 0 must equal `NumPath`; the delay's own extents 1, 2 are taken as before), path data,
    `no_interact`, `interact_coord` (count summed in 64 bits);
  - `CenterFrequency` and position/orientation datasets (`[n_snap, 3]`), the attributes `NumSnap`, `NumTx`, `NumRx`,
    `NumPath`, `Initial_position`, `CenterFrequency`, positions and orientations;
  - `Name`: a fixed-length string of at most 256 bytes, read into a zeroed 257-byte buffer;
  - `ChannelDims`/`Order` in every function (`qHDF_read_index`; product checked against 2^32 - 1);
  - `qHDF_read_data` (rank > 3 gives an empty `std::any`, no `dims[3]` overflow).

  Required: `NumSnap`; `NumTx`, `NumRx` and the positions when `NumSnap > 0`; `coeff_im` together with `coeff_re`;
  `interact_coord` when `sum(no_interact) > 0`. Optional, with their old defaults: `Name` (""),
  `Initial_position` (0), `NumPath` (0), orientations (empty if missing).

  Two more limits for crafted files, beyond the md/bugs.md proposal. Both were needed for the fuzzing acceptance:
  - (a) *Data present.* A dataset must hold the data it declares. A contiguous or compact dataset needs storage for
    every element; a chunked one at least 1/65536 of it; and the storage may not exceed the file size. Without this,
    a 10 kB file that claims a `[2^30, 2, 4]` dataset whose extents match patched attributes would allocate 64 GB
    (tested). The file-size bound was added after the campaign: `H5Dget_storage_size` of a contiguous dataset returns
    the size from the layout message, which is part of the file.
  - (b) *Snapshot padding.* Old files omit the groups of empty snapshots, and the reader pads them with empty
    entries. Snapshot groups are now found by listing the group, not by probing `Snap_0 ... Snap_<NumSnap-1>`.
    A file needing more than 2^20 padded snapshots is rejected. Without this, `NumSnap = 4e9` with one snapshot group
    loops 4e9 times and pads 4e9 entries (tested).

  Repro `B-001`: `numpath: ... dataset 'coeff_re' has extent 50 in dimension 0, expected 1.`;
  `name300: ... attribute 'Name' must be a fixed-length string of at most 256 bytes.`;
  `missing_im: ... dataset 'coeff_im' is missing or cannot be opened.` No ASan report. The release run now ends with
  exit 134: the repro does not catch the exception (uncaught `std::invalid_argument`).
- **B-014.**
  - `hdf5_create` and `hdf5_reshape_layout` compute `nx·ny·nz·nw` step by step in 64 bits. They throw
    `std::invalid_argument("Storage layout has too many slots: nx * ny * nz * nw must not exceed 4294967295.")`
    before any allocation or file access: `hdf5_create` creates no file, and the test checks that.
  - `(65536)^4`, which overflows even 64 bits in one product, is caught too.
  - Readers check the stored layout the same way (`qHDF_read_index`).
  - Slot numbers are computed in 64 bits, and `qHDF_slot` checks `slot < order.size()` before indexing.

  Repro `B-002`: `what(): Storage layout has too many slots ...` from `hdf5_reshape_layout`, no ASan report (aborts:
  uncaught in the repro).
- **B-015.** Writer: the name is copied into a zeroed `char[256]`, truncated to 255 characters, and that buffer is
  written. Reader: `qHDF_read_name` (type and size check, zeroed 257-byte buffer). The ASan suite no longer reports
  `test_hdf_functions.cpp:114`/`:350`. Repro `B-004`: `name length 20: 0 non-zero bytes stored after the terminating
  NUL`, `name length 300: read back with length 255`, in the release and the ASan build, without a report.
- **B-050.** By sub-case:
  - *Empty snapshots / 1 snapshot with 0 paths / trailing empty snapshot.* A per-snapshot field is now written for
    every snapshot when the field is present (vector size = `n_snap`), also if the entry is empty, as a dataset with
    extent 0, plus `NumPath = 0`. The reader restores every entry with its shape (e.g. `delay[1]` stays `[1,1,0]`).
    Older readers read these files correctly: they open the datasets and read 0 elements. Checked with the WP-01
    library, see "Compatibility" below.
  - *Missing `center_frequency`.* The writer keeps the `CenterFrequency` attribute at its default NaN, as before. The
    reader returns an empty vector for a NaN attribute. Older readers still get `[NaN]`, as before.
  - *1-element vectors.* The reader distinguishes `H5S_SCALAR` (scalar) from rank 1 with extent 1 (`arma::Col`). The
    writer always wrote them that way, so there is no format change.
  - *`arma::Row`.* It comes back as `arma::Col`. This was documented already, and I kept it; doc now says it in
    `hdf5_read_dset` too.
  - *Empty string.* It is written as before (size 1, one NUL byte; HDF5 has no size-0 strings) and read back as `""`:
    trailing NUL bytes of fixed-length strings are stripped.
  - *Long parameter names.* They are not rejected (no new error). The reader queries each name's length
    (`H5Lget_name_by_idx` with a null buffer) and reads names of any length, so names over 251 characters are listed
    in full and returned by `hdf5_read_channel`. Old files with long names also read correctly now.
  - Also: element types are matched by class, size and sign, so big-endian or non-native 32/64-bit numbers from
    other tools are read. Unsupported types are still returned as an empty `std::any`.
  - **Needs decision: empty `tx_orientation` / `rx_orientation` come back as `[3, 1]` zeros** (md/bugs.md: "arguably
    harmless"). Proposal: a zero orientation is a valid value, so a NaN sentinel is impossible, and older readers
    would misread a NaN. The only safe format is an extra marker attribute on the channel group, e.g.
    `OrientationEmpty` (bit 0 TX, bit 1 RX), written when the orientation is empty. Older readers ignore it and keep
    returning zeros. The new reader would return an empty matrix, and the MEX/Python readers would then omit the
    field or return an empty array, where scripts may expect zeros today. Not implemented: it changes visible wrapper
    output for a case the item calls harmless. I documented the current behaviour in the C++ doc block of
    `hdf5_read_channel`.

  Repro `B-011`: only `rx_orientation: size 0x0 -> 3x1` / `tx_orientation` (the open sub-case) and
  `par row1: type 51 -> type 41` (documented Row → Col) remain. Not listed any more: the per-snapshot vector
  lengths, `delay[1]`, `center_frequency`, `vec1`, `u32vec1` and `str_empty`.

## Behaviour changes for users

- **`hdf5_write` to an occupied slot replaces the slot completely** (decision B-001 (a)). The old structured data and
  all unstructured datasets of the slot are removed, also those written with `hdf5_write_dset`. Before, a slot that
  held only unstructured data kept it, and new `par_*` data was silently lost. The file does not shrink; run
  `h5repack` to reclaim the space (decision B-052 (a)). This applies to MATLAB/Python `hdf5_write_channel` too.
- **`hdf5_read_dset` / unstructured data of `hdf5_read_channel`.** These also apply to files written before WP-02:
  - a 1D dataset with one element is returned as `arma::Col` (type IDs 40-45) instead of a scalar (10-15). Python
    therefore returns a numpy array of shape `(1,)` instead of a Python scalar. In MATLAB both are 1×1, and the MEX
    tests are unchanged;
  - an empty string written by the library comes back as `""` instead of a 1-character string `"\0"`;
  - fixed-length strings lose trailing NUL bytes, and variable-length strings (h5py, MATLAB) return their text
    instead of 8 pointer bytes;
  - datasets with big-endian or other non-native 32/64-bit integer/float types are now read instead of being ignored.
- **`hdf5_read_channel`.**
  - A channel written without `center_frequency` comes back with an empty `center_frequency` instead of `[NaN]`. This
    also applies to files written before WP-02, where any stored NaN attribute reads as empty.
  - New files keep empty snapshots: every per-snapshot field has one entry per snapshot, with the shape it was written
    with.
- **New errors (`std::invalid_argument`).**
  - `hdf5_create` / `hdf5_reshape_layout` throw for more than 4294967295 slots, and `hdf5_create` creates no file
    then.
  - Malformed files throw instead of corrupting memory: extents that do not match the attributes, missing required
    datasets or attributes, `Name` longer than 256 bytes or not a fixed-length string, datasets declaring more data
    than the file holds, more than 2^20 missing snapshot groups.
  - `hdf5_write` with `assume_valid = true` throws if a position/orientation is non-empty with other than 3 rows, or
    if `coeff_re[i]` and `coeff_im[i]` differ in size (before: over-read).
- **HDF5 failures while writing now throw `std::runtime_error("HDF5 error: ...")`** instead of being ignored.
- **Invalid names or types no longer change the file.** `hdf5_write` and `hdf5_write_dset` reject an invalid name or
  an unsupported type before touching the file (before: the slot could be half written or reserved).
- **The library no longer closes the HDF5 library (`H5close`) and no longer switches HDF5 error printing off for the
  process.** Programs that use HDF5 themselves keep their identifiers and their error handler.
- A channel name of more than 255 characters written with `assume_valid = true` is stored truncated to 255 characters
  (before: 256 bytes without NUL and a reader over-read).
- `hdf5_read_dset_names(fn, nullptr, …)` returns the count instead of crashing.
