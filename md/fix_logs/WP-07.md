## Per item

**B-017.** `qrt_file_init` decided which CIR orientation columns to store on the double (dtype) values, while
`qrt_file_append` re-derived the format byte from the float values in the read cache; an angle such as 1e-50 is
non-zero in double but 0.0f in float, so the two disagreed and append patched the TX table and index 4 * no_cir
bytes off. Now:
- `derive_fmt` in `qrt_file_init` tests `(float)value != 0.0f`, i.e. the value as stored;
- `qrt_file_append` reads the format byte from the file (offset `11 + 16 + 4 * no_freq`) and counts the stored
  columns with the same predicates as the readers (`fmt > 3` bank, `fmt in {2,3,6,7}` tilt, `fmt in {1,3,5,7}` head;
  new helper `qrt_orientation_columns`). Files written by the old `qrt_file_init` (before any append) are therefore
  appended correctly too.
- v4 legacy files: `qrt_file_init` writes only v5/v6; `qrt_file_append` rejects v4 files with
  "qrt_file_append: only v5/6 files can be appended to." (`std::invalid_argument`) before it writes anything (the new
  test checks that the file is byte-identical afterwards); `qrt_file_read_raw` rejects v4 as before. The readers
  decode the v4 format byte unchanged; the v4 test file `tests/data/test.qrt` reads as before (existing "QRT Reader"
  case, B-010 repro: cache/no-cache difference 0).
- Files already corrupted by the old append (`repro/read_corrupt.txt`, files written by the B-007 repro linked with
  the old object): `qrt_read_cache_init` and `qrt_file_read_raw` now throw "orig_index points past the end of the
  file"; `qrt_file_read` without a cache returns TX0 as an unwritten slot (zero positions, 0 paths), because the
  misplaced index entry of slot 0 reads as 0, which is the valid marker of an unwritten slot and cannot be told apart.

**B-048.** All four readers (`qrt_read_cache_init`, `qrt_file_parse`, `qrt_file_read`, `qrt_file_read_raw`) take
the file size once (`rdbuf()->pubseekoff(0, end)`, one call) and compare every count with the bytes that remain
before memory is allocated or a loop runs over it: `no_freq` (4 bytes each), `no_cir` (3 to 6 floats each, per
format byte), `no_dest` (at least 5 bytes each: CIR offset and name length), `no_orig` (3 to 6 floats + 8-byte index
each), the `path_data_index` table of each written origin (`no_cir` x 8 bytes, checked in the cache), every stored
offset (`orig_index`, `path_data_index` entries) against the file size, `no_path` of a CIR (1 + 8 or 2 x 4 x
`no_freq` bytes each) and the sum of the interaction counts (12 + 1 bytes each, 12 in v4). The stream is checked after
the reads; `no_path` and `l_orig_index` are initialised. Messages: "QRT file truncated or corrupt: no_path = 20000000
does not fit into the file.", "... orig_index points past the end of the file.", "QRT file truncated or corrupt.",
all `std::invalid_argument`. The checks are per count and per CIR, never per path; the header parsers track the read
position arithmetically instead of calling `tellg()` (see Speed). `sum_no_int` in `qrt_file_read`
is now 64-bit (it could wrap for very large files once `no_path` is bounded only by the file size). The existing
"unexpected end of file in path block" of `qrt_file_read_raw` is now `std::invalid_argument` instead of
`std::runtime_error`, as the notes ask for malformed files.

**B-049.** The index checks of `qrt_file_read` (cache and file path) compare `i_cir` / `i_orig` as `arma::uword`;
the seek offsets of the file path are computed in 64 bit; `qrt_file_read_raw` compares `i_orig` as `arma::uword`
(it keeps its `std::out_of_range`, as before for indices below 2^32). `i_cir = 2^32` now throws
"CIR index exceeds number of CIRs in file." with and without the cache (before: accepted without the cache,
Armadillo's "index out of bounds" with it).

**B-059.** Documented values of `normalize_M`: 0 and 1 in the C++, MEX and Python blocks (the header comment's
"sum-column power is 2" is B-060, WP-17, not touched). `qrt_file_read` now throws "'normalize_M' must be 0 or 1."
before it opens the file. `add_paths` takes the path count from the first given field, also when it is 0
(`n_path_set` flag instead of `n_path_add == 0` as "not set"), and every later field must match; before, a 0-path
coefficient cube let a later field set the count and left an object that `is_valid()` rejects. No MEX or Python
wrapper calls `add_paths`.

## Behaviour changes for users

- `qrt_file_init`: an orientation column whose values all round to 0 in float is no longer stored (the file is the
  same as for zeros). Before, it was stored as zeros and the next `qrt_file_append` corrupted the file.
- `qrt_file_append` reads the orientation format from the file; files with such a column, written by `qrt_file_init`
  of any version, are now appended correctly.
- QRT readers (`qrt_file_parse`, `qrt_read_cache_init`, `qrt_file_read`, `qrt_file_read_raw`, and the MEX / Python
  wrappers on top of them) throw `std::invalid_argument` ("QRT file truncated or corrupt...") for truncated files and
  for counts or offsets that do not fit the file size, instead of returning zeros or garbage, allocating gigabytes or
  running for minutes. Files corrupted by the old append are now rejected by `qrt_read_cache_init` and
  `qrt_file_read_raw`.
- `qrt_file_read_raw`: an unexpected end of file throws `std::invalid_argument` (was `std::runtime_error`).
- `qrt_file_read`: `i_cir` / `i_orig` of 2^32 or more throw `std::invalid_argument` (were wrapped to 32 bit).
- `qrt_file_read`: `normalize_M` other than 0 or 1 throws `std::invalid_argument` (MEX: error; Python:
  `RuntimeError` from the reader thread); before, any other value behaved like 0.
- `channel::add_paths`: the first given field sets the number of added paths, also when it is 0; a later field with a
  different count throws `std::invalid_argument` (before: accepted, leaving an invalid object). C++ only.

## Found on the way

1. `qrt_file_read_raw` is quadratic in the number of paths per origin: `out.reserve(out.size() + nP)` at
   `src/qd_channel_qrt.cpp:1872` (per-CIR loop of `qrt_file_read_raw`) runs once per
   CIR and reallocates (moving every path read so far) each time, because `reserve` allocates exactly the requested
   size. `repro/raw_scaling.cpp` (one origin, 80 paths per CIR): 60 000 / 120 000 / 240 000 paths take 0.43 / 1.74 /
   7.50 s (factor 4 per doubling; load about 7, provisional). Old and new code alike. Fix: reserve once (sum of the
   path counts) or keep the geometric growth of `push_back`. Proposed severity S3 (performance). Not changed here;
   the benchmark reads origin 0 only.
2. MEX and Python `qrt_file_read` on a valid file with 0 CIRs (`qrt_file_init` accepts `cir_pos` of size [0, 3]):
   `arma::regspace<arma::uvec>(0, arma::uword(cache.no_cir - 1))` at `api_mex/qrt_file_read.cpp:100` and
   `api_python/qpy_qrt_file_read.cpp:127` subtracts in 32 bit, so the default "all CIRs" index vector has 2^32
   entries (34 GB). Under `ulimit -v 8000000`: Python `MemoryError std::bad_alloc`, Octave "out of memory or dimension
   too large for Octave's index type" (`repro/zero_cir.cpp`, `zero_cir_python.txt`, `zero_cir_mex.txt`); without a
   limit on this 121 GB machine it would allocate the vector and then fail on the first read. Expected: empty outputs
   (or a clear error). Proposed severity S3, wrappers (WP-15).
