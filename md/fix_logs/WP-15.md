**B-089 and the WP-06 note (D3).** Both MEX wrappers read `mtl_ind_in` without copy and pass it unchanged, and return
`mtl_ind_out` unchanged (comment "no shift intended", as the spec asks for 1-based C++ indices). Padding entries of

**B-090 (D4).** One static helper in the MEX file, `carriers_to_pilot_grid`, with the Python rules (span = max - min,
reference = `center_freq(1)` when given else the lowest carrier, zero span with more than one carrier is an error
"Values in 'carrier_freq' must span a positive range.", a single carrier uses bandwidth 1 Hz and pilot = offset), used
by the single-frequency and the multi-snapshot branch. The multi-frequency branch passes `carrier_freq` to
`baseband_freq_response_multi` as before (no bandwidth derivation, input order kept). To follow Python exactly, two
MEX-only errors went away: the single-frequency mode no longer requires `center_freq` with `carrier_freq` (reference:

remaining error says "Provide pilot_grid+bandwidth or carrier_freq." (the old MOxUnit check of that text and of the
removed multi-snapshot error were updated). For ascending carriers the arithmetic is identical to the old code
(`max - min = last - first`, same reference), and for one carrier `-1 * (f - fc)` equals the old `-|f - fc| * (+-1)`
bit for bit. No shared C++ helper: the Python wrapper does the same three lines inline; a new library function would
be new public API.

**B-091 (decision a, D5).** `i_irs` defaults to 1; 0 and values above the number of IRS codebook entries (columns of
the IRS coupling matrix) give "Input 'i_irs' must be from 1 to N (1-based codebook port index, one per column of the
IRS coupling matrix)."; the wrapper subtracts 1. A missing IRS coupling matrix is still reported by C++. Python stays

**B-092 (decision a, D6).** `qdant_read_multi` does not check consistency, so the MEX wrapper calls
`arrayant_is_valid_multi(entries, true)` for more than one entry, after the existing output-count check. This is the
library's definition of a frequency set (used by `get_channels_multifreq`) and slightly stricter than D6's minimum: it
also compares element positions and the coupling size. Error: "Entries in file '<fn>' do not form a frequency set
(<detail>); pass 'id' to read single entries." Both documentation blocks state the difference (MATLAB: all entries by
default; Python: ID 1, all entries with `id = 0`). Beyond D6: the Python `id = 0` path had the same gap (an
Armadillo-internal error for different element counts, and for different grids a dict whose pattern size does not
match its grid vectors), so it got the same check and message; pytest covers both cases. Two old MOxUnit tests read
files that are no frequency set without `id` (`test_qdant_read.m` read all entries of a 1- and a 2-element entry;
`test_qdant_write.m` read only the layout of a file with different grids); they now expect the error, or read one
entry by `id` (the layout output is the same).

**B-095 (decision a, D7).** `calc_diffraction_gain` checks first `orig` / `dest` not empty ("Inputs 'orig' and 'dest'
cannot be empty.") and `lod` 0-7 ("Input 'lod' must be 0-7."); before, lod 8 gave the inner "must be 1-7" and empty
input the `xpr_update` message, or (lod 0 without `xprmat`) an empty result. lod 0 is accepted (direct ray only,
coord `[3, 0, n_pos]`), verified by Catch2, MOxUnit and pytest. Both wrappers drop their lod-to-segment table: MEX
passes a local cube and creates the MATLAB array from the C++ size (a 3-D array of `[3, 0, n_pos]` for lod 0; the
generic copy helper would return 0x0), Python copies the C++ cube. The MEX `generate_diffraction_paths` wrapper lets
C++ size the outputs and copies them (it accepts 7; out-of-range and empty input give the C++ messages). Documentation:
C++, MEX and Python give the range 0-7 (generate: 1-7, table row "7 | 1 | 10 | direct line in 10 segments"), and the
`coord` shape as `[3, n_seg-1, n_pos]` with examples (lod 2: 3x2, lod 7: 3x9, lod 0: 3x0). The shape string itself was
right when read with `n_seg` of the generate table (3 for lod 2); the examples remove the ambiguity. The Python block
lists the lod table inline (Python has no `generate_diffraction_paths`).

**B-113 (decision a, D8).** Applies to `get_channels_planar`, `_spherical`, `_multifreq` (`_irs` has no
`add_fake_los_path`). When `add_fake_los_path` is set and all path inputs are empty, each function calls itself with
one dummy NLOS path and copies slot 0 to the outputs, then returns. Slot 0 does not depend on the path data except
through a zero amplitude (spherical / multifreq: delays and angles from the TX-RX element geometry; planar: delays use
the antenna projection in the direction of path 0, so the dummy path lies in the LOS direction). The dummy path is
1 m longer than the TX-RX distance and never detected as LOS. Calls with paths run through unchanged code, so they are
bit-identical (all existing tests pass unchanged). Delay: `distance / c` per antenna pair with
`use_absolute_delays`, else the relative value (0 for co-located phase centres); planar Doppler 0. The Catch2 cases
compare slot 0 with a call that has a real LOS path (moved to slot 0) on 2-element antennas with element positions,
orientation and a 2x1 RX coupling: delays equal within 1e-18 s, angles within 1e-14 (spherical). The three MEX
wrappers now call C++ whenever `n_path > 0` (with `add_fake_los_path` always); 0 paths without it still return empty
outputs (not changed, see "Found on the way" 4). Python planar / spherical called C++ already (and threw); Python
multifreq skipped the call like MEX and now calls it with `add_fake_los_path`. Python spherical batch mode keeps its
documented empty entries for snapshots without paths (noted in its documentation line).

**B-114 (D9).** For struct-array input the MEX wrapper maps usage 3 to 0 and 4 to 1 before
`arrayant_rotate_pattern_multi`, as Python does; the usage table note says so. Without output argument both branches
return the struct (to `ans`); the "Wrong number of output arguments." branch for `nlhs == 0` is gone.

**B-123 (D10).** Both wrappers build the default "all CIRs" index list only for `no_cir > 0`, and compute the last
index in 64 bit. A file with 0 CIRs gives `center_freq` (from the file), `[3, 0]` positions and empty cells / lists

**WP-12 note (D11).** The MEX and Python `icosphere` wrappers run the C++ overflow check (`n_div^2 * 180` must fit into
64 bits) before allocating and throw "Input 'n_div' is too large.". The MOxUnit check requests all four outputs through

**WP-05 note (D12).** `hdf5_write_channel` and `hdf5_read_layout` return `storage_dims` as int64
(`qd_python_copy2numpy<unsigned, py::ssize_t>`, declared return type `py::array_t<py::ssize_t>`), as

## Behaviour changes for users

Breaking changes are marked **[breaking]**.

- **[breaking]** MATLAB `arrayant_generate('multibeam' / 'multibeam_sep')` and Python `arrayant.generate('multibeam')`:
  the default per-element beamwidth is 120° (as documented and as in C++), also when 0 or `[]` is passed; it was 90°.
- **[breaking]** C++ `calc_angular_spreads_sphere`: default `disable_wrapping = true`, `calc_bank_angle = false`
  (wrapping and bank angle off), as in MATLAB and Python; C++ callers relying on the old defaults must pass
  `false, true`.
- **[breaking]** MATLAB `triangle_mesh_segmentation`: padding entries of `mtl_ind_out` are 0 (no material), were 1.
  `triangle_mesh_segmentation` and `subdivide_triangles` pass `mtl_ind` through unchanged (0 stays 0).
- MATLAB `baseband_freq_response` with `carrier_freq`: carriers in any order are accepted and the output keeps the
  input order (descending used to error); duplicate-only carriers give an error (used to give NaN); `center_freq` is
  optional in single-frequency mode and for a single carrier in multi-snapshot mode (reference: the lowest carrier;
  both used to error); error text "Provide pilot_grid+bandwidth or carrier_freq.". Same rules as Python.
- **[breaking]** MATLAB `get_channels_irs`: `i_irs` is 1-based, default 1; 0 and values above the number of codebook
  entries give an error naming `i_irs` and the range. Code that passed 0 for the first port must pass 1.
- **[breaking]** MATLAB `arrayant_qdant_read(fn)` without `id`: a file whose entries are no frequency set (different
  element counts, grids, element positions or coupling sizes) gives an error asking to pass `id`; it used to return a
  struct array of unrelated antennas. Python `qdant_read(fn, id=0)` checks the same (it used to fail with an
  Armadillo-internal error or return an inconsistent dict). Python's default stays ID 1.
- Diffraction `lod` 7 (one direct line in 10 segments) is public: MATLAB `generate_diffraction_paths` accepts it,
  MATLAB `calc_diffraction_gain` returns `coord` of `[3, 9, n_pos]` (was `[3, 0, n_pos]`), Python returns it (was an
  internal error). `calc_diffraction_gain` (all APIs) rejects lod outside 0-7 with "Input 'lod' must be 0-7." and
  empty `orig` / `dest` with "Inputs 'orig' and 'dest' cannot be empty." (C++ used to return empty outputs for empty
  input with lod 0 and no `xprmat`).
- `get_channels_planar`, `_spherical`, `_multifreq` with 0 paths and `add_fake_los_path`: C++ and Python return one
  zero-power LOS path with the LOS delay per antenna pair (C++ and Python planar / spherical used to throw); MATLAB
  and Python multifreq used to return delay 0 regardless of `use_absolute_delays`.
- MATLAB `arrayant_rotate_pattern`: struct arrays accept usage 3 and 4 (as 0 and 1, as in Python); a call without
  output argument returns the result as `ans` (used to error).
- MATLAB and Python `qrt_file_read` on a file with 0 CIRs: empty outputs (used to try to allocate 34 GB).
- MATLAB and Python `icosphere`: an `n_div` whose output size overflows gives "Input 'n_div' is too large." before any
  allocation (some values used to fail with a terabyte allocation).
- **[breaking]** Python `hdf5_write_channel` and `hdf5_read_layout`: `storage_dims` is int64 (was uint32), as
  `hdf5_create_file`. Documentation: `hdf5_read_channel` `no_interact` is int64 (it was already), `has_data` uint32.

## Found on the way

1. C++ `generate_arrayant_multibeam` maps `az_3dB` / `el_3dB <= 0` to 90° (`src/qd_arrayant_generate.cpp:817-818`),
   while its default arguments and documentation say 120°; a C++ caller who passes 0 gets 90°. The wrappers now pass
   120 themselves; the C++ mapping was not changed (decision (a) concerns the wrappers).
2. Python `qrt_file_read` documentation names the arguments `cir` and `orig` (`api_python/qpy_qrt_file_read.cpp:28-36`),
   the binding names them `i_cir` and `i_orig` (`api_python/python_channel.cpp:145`); a keyword call with the
