**B-003.** In the NLOS branch of `get_channels_spherical` (`src/get_channels_spherical.cpp:302`) and
`get_channels_multifreq` (`src/get_channels_multifreq.cpp:390`) one line was added after `d_length` is computed:
`d_fbs_lbs += d_length - d_shortest;`. With `d_shortest = |TX-FBS| + |FBS-LBS| + |LBS-RX|` (phase centres) this is
exactly the proposed `d_fbs_lbs = d_length - |TX-FBS| - |LBS-RX|`, written so that for paths with
`path_length <= polyline` the added term is exactly 0 and the result is bit-identical to the old code (the benchmark
G2 confirms: checksums equal). The phase-centre length is now `max(path_length, polyline)`; the per-element spherical
offsets (`dt` per TX element, `dr` per RX element) are unchanged. The LOS test still uses `d_length`, as before.

  delays (`src/get_channels_irs.cpp:180-237`, combination loop below), so it follows without a code change; the new
  IRS test checks `delay * c = L1 + L2` and the phase for path lengths longer than both polylines and for 0.

  (`src/get_channels_planar.cpp`, coefficient loop), i.e. the given length for the phase centres plus planar element
  offsets. It is correct and was not changed (there is no geometry; values shorter than the TX-RX distance are taken
  as given).

  TX-RX distance, so the negative-delay bound and the `quantize_delays` limit are unchanged; NLOS delays only grow.

**B-019.** Documentation only (decision (a)). The `remove_delay_phase` input of `baseband_freq_response_multi` (C++),
the multi-frequency mode of the MEX `baseband_freq_response`, and `remove_delay_phase` of Python
`channel.baseband_freq_response` now say that the channels must be generated with `use_absolute_delays = true`, and
why: the coefficients of `get_channels_*` always carry the phase of the absolute path length, while `delay` holds the
relative delay when `use_absolute_delays = false`; the undo then leaves `exp(-j 2 pi f d_LOS / c)` in the coefficients,
which is interpolated across the coarse `freq_in` grid and aliases (magnitudes stay right). The same note is in the
`get_channels_multifreq` blocks (C++, MEX, Python) and in the header comments. The Catch2 case is the absolute case
of the C-2 repro: max |H_multi - H_true| = 9.8e-8 (< 1e-5).

**B-020.** Phase in double precision, reduced to one period, in both kernels; only `baseband_freq_response` (and thus
`_vec`, the MEX / Python single-frequency and multi-snapshot modes) uses them.
- `baseband_freq_response.cpp`: the float `phasor = -2 pi B p` array is replaced by a double array
  `freq[k] = -bandwidth * pilot_grid[k]` (same aligned allocation as before, now 8 bytes per carrier).
- AVX2 kernel (`src/baseband_freq_response_avx2.cpp`, compiled with `-mavx2 -mfma` as before): per block of 8
  carriers the 8 frequencies are held in two `__m256d`; per path `x = freq * delay` (double), `x - round(x)`
  (`_mm256_round_pd`, nearest), converted to float (exact to 3e-8 cycles). sin / cos of `2 pi r`, `r` in
  [-0.5, 0.5], come from a local `qd_sincos_2pi_reduced`: quadrant `q = nearest(4 r)` (exact in float), `t = (4 r - q)
  pi/2` in [-pi/4, pi/4], the Cephes polynomials of `_fm256_sincos256_ps`, quadrant swap and signs. The general
  `_fm256_sincos256_ps` (with its own Cody-Waite reduction) is no longer used here, and `fastmath_avx2.h` is no longer
  included by this file; `fastmath_avx2.h` itself is unchanged, so SOS, `fast_sincos` and the ray kernels are
  unaffected.
- Generic kernel (`src/quadriga_lib_generic_functions.hpp`): the same algorithm in scalar C++ (new inline
  `qd_sincos_2pi_reduced(float, float&, float&)`, branch-free), with the carrier loop innermost (paths outer, the
  accumulators are the output rows `Hr`/`Hi` of the antenna). The double rounding uses the magic-number method
  `x - ((x + 1.5 * 2^52) - 1.5 * 2^52)`, exact for |x| < 2^51; gcc vectorizes this loop with SSE2 in the generic build
  (`-fopt-info-vec`: "loop vectorized using 16 byte vectors"). Paths whose phase may reach 2^50 cycles
  (`|delay| * max|freq| >= 2^50`) or whose delay is not finite use a scalar loop with `std::rint` and `std::sin` /
  `std::cos`, so NaN / Inf delays still give NaN, as before. The other users of the header (SOS, ray kernels) are
  unchanged: the header only gained this inline function and the changed `qd_DFT_GENERIC`.
- Accuracy (repro C-3, one path, |H - exp(-j 2 pi B tau)|): AVX2 and generic 1.1e-13 / 8.3e-12 / 1.4e-10 / 1.65e-8
  at tau = 1 us / 100 us / 2 ms / 0.12 s (before: 1.2e-5 / 1.5e-3 / 0.064 / 0.31). Benchmark workloads
  (100 paths, |c| ~ 0.14): max error vs the double reference 2.8e-6 (AVX2) / 1.9e-6 (generic), before 9.5e-5; at
  10 ms delays 3.2e-6, before 0.93.
- Acceptance "AVX2 and generic agree to 1e-6 for delays up to 10 s" (`crossbuild/`: the same program linked against
  `build_linux/libquadriga.a` and `build_generic/libquadriga.a`, 256 random pilots, B = 1e8 or 1e9, unit-power
  channels): 10 paths with delays up to 10 s or 1 s: max |H_avx2 - H_generic| = 4.9e-7 / 4.8e-7 (|H| up to 2.5),
  also at B = 1e9 (4.8e-7). With 100 paths (16x16) the difference is 2.2e-6 (|H| up to 3.4), and 4.8e-6 for 20
  unnormalised randn paths (|H| up to 16.7). This residual does not depend on the delay: with all delays below 1 ns
  (phase about 0) it is the same (2.4e-6 and 3.4e-6), and the old code at 9e5af26 gives the same values there
  (2.4e-6 / 3.4e-6). It is the rounding of the single-precision sums (about 1e-7 relative per addition over 2 n_path
  additions; FMA in AVX2, separate multiply and add in the generic build), which this package did not change. The
  delay-dependent difference is gone: the old code differed by up to 1.5e12 between the builds at 10 s (the AVX2
  `_fm256_sincos256_ps` with huge arguments, B-026). So the criterion holds for the phase; for many paths or large
  |H| the float sums limit the agreement to about 1e-6 relative to sum |c|. Accumulating in double would change
  that, at a cost in the AVX2 kernel; not done (manager / user decision if the criterion is meant to include it).
- B-026 route: `baseband_freq_response` no longer passes large arguments to `_fm256_sincos256_ps`; the reduced
  argument is at most 1/2 cycle. The other B-026 routes (`fast_sincos`, `fast_geo2cart`) are untouched (WP-08).
- Catch2: the md/bugs.md test (tau = 0.12 s, B = 1e8, pilots {0.5, 1}, error < 1e-4) passes in both builds, also in
  float; the 10 s case (2x2, 4 paths with delays from 1 us to 10 s, 64 carriers, per-antenna delays) is within
  5e-7 of the double reference in both builds, planar-wave delays `[1, 1, n_path]` give the same result as
  identical per-antenna delays, NaN / Inf delays give NaN (as before) and a phase beyond 2^50 cycles (1e8 s) stays
  finite with |H| = 1 (generic fallback loop).
- Docs: "Internal arithmetic is single-precision" is replaced by "the phase is computed in double precision and
  reduced to one period before sin / cos are evaluated in single precision; coefficients and sums are single
  precision" (C++ `baseband_freq_response`, `_vec`, header; MEX; Python).

**B-068.** Documentation only; the 0-path case (B-113) is unchanged. All blocks (C++, MEX, Python of spherical,

     without the receive mirror, and are inverted (co / cross swapped) for `M` from `get_channels_*` / the ray
     tracer. This is beyond the row naming; it needs a decision (and probably an item of its own).

and scalar libm calls keep the generic loop from being vectorized (x3.2). Only the helper variant meets the limits; the

`baseband_freq_response_avx2.cpp` and `quadriga_lib_generic_functions.hpp`, restored into `src/`). After the restore,
all builds were rebuilt and every suite was re-run (numbers in "Suites").

**Proposed for WP-08 (de-duplication with `fastmath_avx2.h`).** The Cephes sin / cos polynomials and the quadrant
reconstruction now exist four times: twice in `src/fastmath_avx2.h` (`_fm256_sincos256_ps` and the
"identical ... after its range reduction" tail of `_fm256_sincos256_pd`), in the AVX2 helper of
`baseband_freq_response_avx2.cpp`, and as scalar code in `quadriga_lib_generic_functions.hpp`. WP-08 changes
`fastmath_avx2.h` for B-026 anyway; there, the polynomial and reconstruction part should become one shared inline
function (taking the reduced argument and the quadrant), used by `_fm256_sincos256_ps`, `_fm256_sincos256_pd` and a
small reduced-argument entry point for `qd_DFT_AVX2`, so that the local helper in `baseband_freq_response_avx2.cpp`
goes away. Checks: bit-identical results for the existing users (SOS, `fast_sincos`, ray kernels) and the WP-04
benchmark F1-F4 unchanged. The scalar generic copy stays (it must be branch-free C++ for vectorization), but its
comment should point to the shared AVX2 code.

## Behaviour changes for users

- **B-003: `get_channels_spherical`, `get_channels_multifreq` and `get_channels_irs` (C++, MATLAB, Python) now use
  `path_length` for NLOS paths.** The delay and the phase of the TX/RX phase centres are `max(path_length,
  |TX-FBS| + |FBS-LBS| + |LBS-RX|)`; before, they were always the TX-FBS-LBS-RX polyline, whatever `path_length` was.
  This changes the delays and phases (and everything derived from them: frequency responses, quantized taps, delay
  spreads) of every NLOS path whose `path_length` is longer than its polyline, which is the normal case for
  ray-tracing input with more than two interactions (`qrt_file_read`, `coord2path`: FBS = first, LBS = last
  interaction, `path_length` = full length). Paths with `path_length` 0 or shorter than the polyline, LOS paths, and
  `get_channels_planar` are unchanged.
- B-020: `baseband_freq_response` (C++ `baseband_freq_response`, `_vec`; MATLAB / Python single-frequency and
  multi-snapshot modes) computes the phase in double precision. Results change slightly for all inputs (by the old
  float phase error, about 1e-5 at 1 us delay and 100 MHz) and substantially for long delays (0.06 at 2 ms, 0.31 at
  0.12 s before; now below 1e-7 for one path). The generic (non-AVX2) build is now about 3 times faster for this
  function; the AVX2 build is about 3% slower.
- B-019, B-068, B-069: documentation only, no change of results.
