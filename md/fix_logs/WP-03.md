## Per item

**B-002.** The delay check sits in the loop that computes the tap index (step 1), on the same value that is converted
to `unsigned`: `if (!(delay > -tap_spacing/2 && delay * (1/tap_spacing) < 2^31)) throw std::invalid_argument`. The
negated form also catches NaN and Inf. The message says which case it is ("contains NaN or Inf values", "a value at or
below -tap_spacing / 2", "a value of 2^31 taps or more (delay / tap_spacing must be below 2^31)"). A delay with
`-tap_spacing/2 < d < 0` is set to tap value 0 before `floor`, so it gets fractional offset 0: interpolation weight 1 on
tap 0 and 0 on tap 1, and the nearest tap is also 0. Every path then lands in tap 0 with its full coefficient, whether
the grid uses the interpolated or the rounded taps. How this fits the interpolation: two-tap interpolation spreads a
delay over the taps `floor(d)` and `floor(d) + 1`; for a negative delay these would be taps -1 and 0, and tap -1 does
not exist. Clamping moves the path by less than `tap_spacing / 2`, which is the same error bound as the nearest-tap
rounding that the function uses whenever interpolation is off or a neighbour tap is missing. At `d <= -tap_spacing/2`
nearest-tap rounding itself would need tap -1, so that is where the error starts (decision (a)).
Upper bound: 2^31 taps. The tap index arrays stay `unsigned` (4 bytes; changing them to 64 bit would cost memory
bandwidth in the hot loops), and with `delay / tap_spacing < 2^31` both `floor` (at most 2^31 - 1) and `floor + 1` fit
without wrap; all float-to-integer conversions are defined. The bound is in taps, so it scales with the tap spacing:
10.7 s at 5 ns, 12.4 h at 48 kHz (acoustic); a test runs acoustic delays of 30 s at 48 kHz.
Also checked now: `tap_spacing` must be finite, and `1 / tap_spacing` too (a NaN `tap_spacing` passed the old
`<= 0` check and produced NaN tap values, i.e. the same undefined conversion).
Documentation: the `get_channels_spherical` sentence now says that the LOS delay of the phase centres is subtracted
and that element pairs closer than the phase centres get slightly negative delays, which `quantize_delays` maps to
tap 0 (C++, MEX, Python). `get_channels_multifreq` and `get_channels_planar` compute per-element delays minus the
phase-centre distance in the same way (`get_channels_multifreq.cpp:834`, `get_channels_planar.cpp:301`), so they
got the same note; `get_channels_irs` subtracts the direct TX-RX phase-centre delay (`get_channels_irs.cpp:243-248`, 316),
and its MEX block had the same wrong "minimum delay" sentence: corrected in MEX, and the bullet added to the C++
block, which had none (there is no Python IRS wrapper). Only documentation was changed in these four functions.

**B-054.** No allocation or loop over the absolute delay range is left; the work depends on the number of entries and
taps only.
- `find_optimal_delays` uses a new helper `accumulate_pdp`. It sums the power per tap in a dense vector over
  `[min index, max index]` of the entries (not `[0, max]`) when that range is at most `4 n + 64` entries, and otherwise
  sorts the (tap, entry) pairs and sums runs (sparse, `O(n log n)`). Both sum each tap's entries in entry order,
  starting from 0.0, which is exactly the order of the old dense loop, so every sum is bit-identical.
- The "interp-only" search, which compared every interpolated tap with every rounded tap, is a merge of the two sorted
  lists now (same result and order).
- Line 545 (`tap2pos(max_grid_val + 2)`, allocated per antenna pair over `[0, max tap]`): replaced by a lookup over
  the grid's own index range `[grid.front(), grid.back()]`, in one buffer reused for all pairs, when that range is at
  most `4 n_grid + 1024`; otherwise a binary search in the sorted grid. Same membership results as before.
- `max_no_taps = 0` (unlimited) still uses "largest absolute tap index + 1" as the budget, as before, so results stay
  identical. This has no visible effect of the offset: the interpolated tap set always contains every rounded tap, so
  when the rounded taps fill `[0, max]` both branches return the same set.
- Results for valid non-negative input: **identical** (bit for bit), not just within 1e-12. Evidence: the benchmark
  checksums (relative difference 0 on Q1-Q9), and `build_linux/scratch/fix/WP-03/diff/diff_qd`, which links the old
  code (renamed by macro) and the new one and compares all outputs with `memcmp`: 36000 cases (float and double,
  seeds 1-3, shared and per-antenna delays, 1-4 x 1-4 antennas, 1-4 snapshots, `fix_taps` 0-3, `max_no_taps` 0, 1, 3,
  8, 48, `power_exponent` 1 and 0.5; delays within 1 us, over 200 us (sparse path), on the grid, 1 us + 200 us
  offset, and 0-4 paths over 0.2 ms with empty snapshots): "36000 cases, 0 differ (bit-wise)".
- The B-054 test uses binary-fraction tap spacing, delays and offset (2^-28 s, multiples of 2^-36 s, 2^-6 s), so the
  shift is exact; it checks equal coefficients and delays shifted by exactly the offset for shared and per-antenna
  input, all `fix_taps`, `max_no_taps` 8 and 48, both exponents; plus a generous timing guard (< 1 s).

**B-055.** The outputs are built in three local vectors and moved into the output arguments at the very end, after
the last read of any input, so any output may alias any input, also across arguments (tested: in place, `delay_quant ==
coeff_re` with `coeff_re_quant == delay`, and a rotation of all three; shared and per-antenna; four delay patterns;
all `fix_taps`). The C++ doc block says that aliasing is allowed. Addition not in the notes: two *outputs* that are

objects"); before, the second assignment silently overwrote the first. No case needed a "needs decision".
The MEX and Python wrappers always pass fresh output vectors, so aliasing is a C++-only topic and is not mentioned in
their blocks.

**B-103.** The C++ MD table and the `delay_quant` output line, the MEX table and `delay_q` line, and the Python
`delay_q` line now say that `[1, 1, n_taps]` (MEX `[1, 1, n_taps, n_snap]`) applies only to shared `[1, 1, n_path]`
delay input with `fix_taps` 1 or 2, and that per-antenna input gives `[n_rx, n_tx, n_taps]` with identical values
for all pairs.

Documentation of `quantize_delays` (C++, MEX, Python): valid delay range, the clamp rule and why, the errors, the

## Behaviour changes for users

- `quantize_delays` accepts delays in `(-tap_spacing/2, 0)` and puts them into tap 0 (before: segfault).
- `quantize_delays` throws `std::invalid_argument` (MATLAB: error; Python: `ValueError`) for NaN or Inf delays (before:
  the path was silently dropped), for delays at or below `-tap_spacing/2` (before: segfault), for delays of 2^31 taps
  or more (before: `bad_alloc` or a multi-GB allocation, or wrapped indices), for a NaN, infinite or so small
  `tap_spacing` that its inverse overflows (before: undefined conversion), and when two outputs are the same object.
- Large absolute delays no longer cost time or memory (20 ms offset: 8.8 s -> 30 ms on the benchmark).
- Outputs may alias inputs (before: wrong first tap in some cases).
- Results for valid non-negative input are bit-identical to before.
