## Per item

**B-006 (AVX2 over-read, per-element angles).** In the general path of `qd_arrayant_interpolate_avx2`, the last,
partial block of elements now loads the per-element angles with `_mm256_maskload_ps` (float) or through a zeroed
`alignas(32)` buffer of `n_valid` values (double), as the angle-vectorised path already did. Full blocks are
unchanged. ASan: no report in the new case and in the suite; A-01 runs clean.

**B-007 (generic kernel, NaN / Inf angles).** The azimuth bracket search now tests `!(grid[0] <= az)` instead of
`grid[0] > az`: a NaN azimuth (which every non-finite input angle or orientation produces, through sin / cos / atan2)
takes the "before the first grid point" branch, whose indices are in bounds; the NaN weights then give NaN in all four
field outputs and `dist`. The elevation search was already in bounds for NaN. This is one comparison per angle and
element outside the pattern loop, no extra branch; the benchmark shows no change (K1, K2 below; checksums
bit-identical). The AVX2 kernel already returned NaN and stayed in bounds (`probe/nan_avx2.cpp`). The test checks
NaN output, no exception, and that finite angles in the same call give the same values as a call without the
non-finite ones.

**B-008 (`append` coupling).** New inline helper `qd_arrayant_coupling_block_diag` in `src/qd_arrayant_functions.hpp`:
zeroed `[n_el1 + n_el2, n_ports1 + n_ports2]` matrices, each block from the input's coupling, an identity block for an
empty `coupling_re`, zeros for an empty `coupling_im`. `append` and `arrayant_concat_multi` both call it (the plan
asked to reuse the assembly of `arrayant_concat_multi`; a shared helper does that without copying the code). Side
effect in `arrayant_concat_multi`: inputs with an empty `coupling_re` (accepted by `arrayant_is_valid_multi`) used to
throw "Mat::submat(): indices out of bounds or incorrectly used" and now get identity blocks (checked with the old
source, `probe/concat_empty.cpp`; covered by the second B-008 case). The output of `arrayant_concat_multi` for
non-empty couplings is unchanged (MEX and Python concat tests pass).

**B-009 (`rotate_pattern` metadata).** With an output, `set_size` now uses the input's port count and the output gets
the input's `coupling_re`, `coupling_im`, `center_frequency` and `name` (assigned explicitly, so an output that
already had the same size does not keep its old coupling). When a single element is written to the output, the
output gets identity coupling (1 x 1), and the centre frequency and name of the input (manager default; documented in
the C++ block). In place with a grid update, `set_size(..., coupling_re.n_cols)` keeps the coupling. The MEX and
Python wrappers rotate in place, so they are affected only by the grid-update case; their docs say that coupling,
centre frequency and name are kept.

**B-010 (`calc_beamwidth_deg`).** Both cuts are searched outwards from the maximum of the cut until the power drops
below the threshold (main lobe only).
- Azimuth: circular when the azimuth grid covers the full circle (gap between last and first grid point not larger
  than the largest grid step, or a single azimuth sample); then 100 · n_az samples over 360°, which for the usual
  [-180°, 180°] grid are the old sample positions without the duplicate at +180°. Otherwise the old linear sampling
  from the first to the last grid value. A cut that is above the threshold everywhere gives 360° (omni patterns; a
  beam towards a pole, where the azimuth cut at the elevation of the maximum is a single direction).
- Elevation: the cut is the great circle through the maximum (azimuth of the maximum, and across the poles the
  opposite azimuth) when the grid has samples at both poles, else the old linear cut. Its sample step equals the old
  one for a full [-90°, 90°] grid. The result is capped at 180°, so omni and dipole-like patterns keep their old
  values (180°, 90°).
Results for beams that do not wrap are unchanged: A-07 boresight 89.83 / 89.86 as before; all existing beamwidth
tests (Catch2, MEX, Python) pass unchanged. Heading 180°: 89.83 / 89.86 (before 360.00); zenith: `bw_el` 89.24 (before
44.62), `bw_az` 360 (documented). The azimuth pointing angle of a beam exactly at a pole is arbitrary (A-07: -108°),
as before.

**B-011 (multibeam towards a pole).** The beam-pointing loop stores the weights of its first iteration (the start
angles) unconditionally (`gain_new > gain || lp == 0`); later iterations still need a gain improvement. Beams at
±90° now give 1 port (pol 1) and 2 ports (pol 2, 3) with finite, non-zero coupling, also with `separate_beams`.
Beams elsewhere: the first iteration already improved on gain 0, so nothing changes (the existing multibeam tests
pass with the same values).

**B-044 (ULA / 3GPP with a custom pattern).** After copying and validating the custom pattern,
`generate_arrayant_ula` and `generate_arrayant_3GPP` reset its element positions to zero and its coupling to
identity, as the C++ docs say (manager default). MEX and Python docs of `arrayant_generate` now say the same. The
built-in patterns (and `generate_arrayant_multibeam`, which passes a 1-element custom pattern) are not affected.

**B-046 (absolute thresholds).** `remove_zeros` computes the power pattern in double precision (float patterns of
amplitude 1e-20 no longer underflow) and removes rows / columns whose summed power does not exceed 1e-12 times the
peak power of a single sample (summed over field components and elements); an all-zero (or NaN) pattern keeps all
rows and columns, so no empty matrices and no zero-size `memcpy`. `calc_directivity_dBi` drops the 1e-14 floor:
0 dBi only when the peak or the weighted sum is 0. Effect on normal patterns: old vs new `remove_zeros` and
directivity of the probe patterns (`probe/rz_compare_old.txt`, `rz_compare_new.txt`): narrow high-gain beams lose a few more outer rows and columns (all below 1e-12 of the peak, i.e. -120 dB, by
construction), wide patterns are unchanged, directivity unchanged in all cases:

## Behaviour changes for users

- `arrayant::interpolate` (and everything built on it: `rotate_pattern`, `combine_pattern`, `get_channels_*`, MATLAB
  `arrayant_interpolate`, Python `arrayant.interpolate`): NaN or infinite angles give NaN for that angle (and element);
  before, the generic kernel also returned NaN but read memory before the pattern buffer. Now documented.
- `arrayant::append` (MATLAB `arrayant_concat`, Python `arrayant.concat` for single-frequency input): the coupling is
  block-diagonal for arrays whose number of ports differs from the number of elements (before: off-block entries of 1
  remained, giving wrong channels); an empty `coupling_im` is treated as zeros (before: crash).
  `arrayant_concat_multi` with an empty `coupling_re` gives identity blocks (before: Armadillo exception).
- `arrayant::rotate_pattern` with an output object keeps the coupling (ports), centre frequency and name (before:
  one port per element, 299792458 Hz, empty name); one element rotated into an output gets identity coupling. In
  place with a sampling-grid update (usage 0 / 1 on non-uniform grids, also in MATLAB and Python) keeps the coupling
  (before: reset to one port per element).
- `arrayant::calc_beamwidth_deg` (MATLAB `arrayant_calc_beamwidth`, Python `arrayant.calc_beamwidth`): the width is
  that of the main lobe only (side lobes above the threshold are no longer included); beams across ±180° azimuth and
  across the poles are measured correctly (before 360° or about half the width); an elevation beamwidth is at most
  180°; a pattern with a single azimuth sample gives 360° (before 0°).
- `generate_arrayant_multibeam` (MATLAB / Python `arrayant_generate('multibeam')`) with a beam at elevation ±90°:
  correct port count and weights (before: one port per element for pol 1, crash for pol 2 and 3).
- `generate_arrayant_ula` and `generate_arrayant_3GPP` (MATLAB / Python `arrayant_generate('ula' / '3gpp', ...,
  pattern)`): element positions and coupling of a custom pattern are ignored, as documented (before: positions were
  kept and added to the array geometry, coupling was kept and extended). Callers whose custom pattern had non-zero
  positions or non-identity coupling get a different array.
- `arrayant::remove_zeros` (also called by `rotate_pattern` with a grid update): the threshold is relative to the peak
  power (1e-12 of the peak sample power), so low-level patterns keep their non-zero samples; an all-zero pattern is
  returned unchanged (before: emptied, 0 x 0). Patterns with a peak power above 1 (high-gain beams) may lose a few
  more outer rows and columns, all below -120 dB of the peak. `calc_directivity_dBi` (MATLAB / Python `calc_directivity`) is independent of the pattern scale (before:
  0 dBi below a peak power of 1e-14).
- `arrayant::copy_element` throws for a read-only object and for an empty destination (before: copied anyway / an
  Armadillo message "Mat::max(): object has no elements").

## Found on the way

- `remove_zeros(&output)` does not copy `name` to the output (`src/qd_arrayant.cpp:1591`; only `center_frequency` is
  copied). `rotate_pattern` is not affected (it calls `remove_zeros` in place on its output). Not changed.
- `remove_zeros`: the azimuth spacing to the previous sample for the first grid point is computed as
  `grid[0] + grid[n_az - 1]` (`src/qd_arrayant.cpp:1433`, and the next spacing of the last point the same way), not
  `grid[0] + 2 pi - grid[n_az - 1]`; for symmetric [-180°, 180°] grids both are 0, for other grids the
  neighbour-keeping rule uses a wrong spacing. Not changed (effect not measured).
