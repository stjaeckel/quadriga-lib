## Per item

**B-121.** `test_bin` gets `BUILD_WITH_AVX2=1` only when the library is built with AVX2 (`if(BUILD_WITH_AVX2)`, the
same variable that is passed to the library as 0 or 1). `build_generic` has no definition (checked in `flags.make`).
The test files needed no change; they call the kernels through `quadriga_lib_avx2_functions.hpp`, which has no
intrinsics. The three AVX2 cases, run before any kernel change (`logs/b121_avx2_cases.txt`): "RTI Internal - AVX2
comparison" 20 assertions, "RPI Internal - Simple Mode (AVX2 vs GENERIC)" 81, "RPI Internal - Dense Grid (AVX2 vs
GENERIC)" 1281, all passed. They do not expose B-071 (their scenes have no exact ties); no unexplained failure.
`BUILD_WITH_CUDA` has the same pattern (library 0/1, tests `#ifdef`); left alone, no CUDA build here.

**B-071.** In `rti_moller_trumbore_update` (shared by float and double AVX2) all six reduction steps of FBS and SBS
use the lane mask `rti_lex_less`: keep the own lane when `W < Wp`, or `W == Wp` and index `< Ip`. Step 3 permutes W
and the indices differently in the lanes 1-7, but only lane 0 is extracted and all lanes still carry the minimum W.
Across blocks the strict `Wm < W_fbs` / `W_sbs` comparisons keep the earlier (lower) block, so the result is the
generic kernel's order (FBS = lowest index, SBS = next lowest at a tie). The comparisons run only after the early exit
(hits are rare), no measurable cost (R1 below).

**B-072.** Both kernels fold the three slabs with NaN-ignoring max / min, starting from -inf / +inf (AVX2:
`_mm256_max_ps(t, acc)` returns `acc` when `t` is NaN). The per-slab sort and the acceptance conditions are unchanged,
so every ray without a 0·inf product gets the same mask (R1 and R3 checksums bit-identical). One addition to D4: a
direction component of -0 (destination -0.0 and origin +0.0) made the slab (NaN, -inf) unsorted, so -inf ended up as
the upper limit and the ray was still rejected. The inverse direction is now `1 / (d + 0)`, which turns -0 into +0
and changes nothing else (the triangle test keeps the original direction). Covered by case 2 of the test. The CUDA
kernel has the same fold (`ray_triangle_intersect_cuda.cu:226-230`): noted, not changed.

**B-027.** Variant (ii) of D1. The double specialisation keeps the origin in double (`__m256d`) and forms
O - T, U - T, V - T and the AABB limits minus O in double before narrowing to float (`_sub8_cvt_pd_ps`); W stays in
the original frame; float input and CUDA unchanged. The first, fused version cost 14 % (R2 1.137, step 2 below). The
recorded second variant computes the edges U - T and V - T (double difference, then float) once per call into a
6 x n_mesh float cache when `n_ray * 16 >= n_mesh`; the triangle loop then forms only O - T in double and loads the
edges. With few rays (or for the tail block) the loop forms the edges itself in the same way, so both paths give
identical values (old-vs-new dumps of step 2 and step 3 bit-identical). Cost: 24 bytes per triangle for the call,
O(n_mesh) conversion (OpenMP from 65536 triangles). Result: R2 0.82 of the old time. Accuracy: the Catch2 case (10 m
cube, 2000 random 30 m rays) gives max |FBS_AVX2 - FBS_GENERIC| = 2.13e-6 m at the origin, 5e6 and 1e7 (old 2.5e-6 /
5.1 / 9.7 m); `probe/rti_offset.cpp` (the rti_random scenes, double) max |W_AVX2 - W_GENERIC| = 7.85e-7 / 1.36e-6 /
1.35e-6 at 0 / 5e6 / 1e7, ratio 1.7 (limit 2), no fbs_ind / sbs_ind difference (old: 1.23e-6 / 0.506 / 0.835, 6569
and 7301 rays with different indices). D-2 passes at (5e6, 5e6) and (1e7, 1e7). The precision statement of the C++,
MEX and Python blocks and of `include/quadriga_tools.hpp` (this is B-108 point 3) now says: AVX2 and CUDA compute in
single precision, GENERIC in the input precision; for double input the AVX2 precision depends on the scene size, not on
the distance from the origin; CUDA rounds the coordinates, so its errors grow with the distance. (CUDA was not changed,
so the D1 wording "AVX2/CUDA ... scene size" would be wrong for CUDA.) The blocks also say that edges and vertices
count as hits and that hits at equal distance come in index order (B-071).

**B-028.** Implemented as D2: the 3-D hit is judged against the plane of the face that produced it (endpoint on that
plane or both endpoints on it: rejected), and a rejected first hit falls back to the second hit (`sbs_ind`, requested
from `ray_triangle_intersect`; one more output, cheap), which is judged the same way. The coplanar 2-D branch only adds
hits (sets 1 where there was no hit), never clears.
Deviation: D2 taken literally reports overlaps for touching boxes. The guard case (4 configurations: box shifted by
half its width along the shared face, shifted in two directions, larger touching face, larger and off-centre) failed
with all 4 (`3D Intersect ... @ F:11 ... vs. E:2`): the diagonal of the touching face lies in the shared plane and
crosses the first box's crease, which the edge-inclusive triangle test reports as a hit on a side face whose plane the
edge does not touch. The old code hid this with "any coplanar face clears every hit of the edge" (which is also why
it missed B-028's genuine hit). Added rule (in the same per-hit check, not in the 2-D branch): a 3-D hit on face G is
also rejected when the edge lies in the plane of another face F of the same object and G does not reach through that
plane (no vertex of G more than `tolerance` on both sides). Such a hit can only be on G's boundary, i.e. a graze.
For a convex object this is exactly what the old clear did; for a non-convex object whose face plane cuts through the
object elsewhere, a genuine crossing of G's interior is kept (the old code cleared it). So the rule clears a subset of
what the old code cleared and no touching case of the suite or the guard reports an overlap; the tetrahedron of D-3
reports (1, 2) in both builds. The check scans the faces of object 1 only for edges with a 3-D hit. Please confirm or
decide otherwise (alternative: D2 literally, accepting false positives for touching boxes with offset).
Also in the rewritten lines: when `ray_triangle_intersect` fails inside the OpenMP loop (error re-thrown after the
loop), the empty hit vector was dereferenced; the pair is now skipped (guard `hit.n_elem != n_edges`).

**B-073.** The AVX2 kernel reads each sub-cloud in blocks of 8 from its first point and discards lanes with
`i_point + i >= i_point_end` (the end of the sub-cloud, `n_point` for the last one) in the hit loop, where the padding
check was; no cost on the hot path (the check runs only for hit lanes). The alignment check in
`ray_point_intersect.cpp` is gone; the point arrays are allocated `n_point + 7` (a block may now start anywhere), and
the kernel comment says so. Aligned input keeps the same code path (P1 0.99, outputs identical). Docs of
`ray_point_intersect` and `point_cloud_segmentation` (C++, MEX, Python): sub-clouds need not be aligned, `vec_size`
padding only improves speed. The existing assertion in "Ray-Point Intersect - Input Validation" that a misaligned
sub-cloud throws for kernel 2 now checks that it is accepted and equals GENERIC.

**B-077.** Empty mesh with empty `obj_ind` (0 x 9 or 0 x 0): returns an empty `uvec` and clears `reason` (size 0),
before the other checks. A non-empty `obj_ind` with an empty mesh still throws the size mismatch.

**B-078.** `subdivide_triangles` throws `std::invalid_argument` "Input 'n_div' is too large." when
`n_in * n_div^2 * 9` overflows 64 bits (checked by division), before any allocation; `icosphere` checks
`180 * n_div^2` before any `set_size`; `cube` / `plane` through `subdivide_triangles`. A count that fits into 64 bits
but not into memory (`n_div = 2^30`, 2^60 * 9 values) gives Armadillo's `std::bad_alloc`, no crash (asserted with
`CHECK_THROWS`). The MEX and Python `icosphere` wrappers pre-allocate `20 * n_div * n_div` outputs before the call;
for huge `n_div` that product wraps, but the C++ check throws before anything is written (MEX test
`icosphere(2^32)` gives the new message).

**B-079.** `ray_triangle_intersect`: when `fbs` or `sbs` is the same object as `orig` or `dest`, the six coordinate
columns are copied before the first output is written (this also covers the second path, `orig` with 4 columns /
`dest` with more rows, where `set_size` frees the input). Outputs with the right size are written in place.
`subdivide_triangles`: all inputs are validated (n_div, overflow, `mtl_ind` length) before the first `set_size`; when
`triangles_out == triangles_in` or `mtl_ind_out == mtl_ind`, the input is read from a copy. For `n_div = 1` the
output keeps the input's memory (asserted). Documented in the C++ blocks; results equal the non-aliased call
(asserted exactly).

**B-081.** C++ block and header: `obj_ind` holds any object IDs per triangle (e.g. the 0-based `obj_ind` of
`obj_file_read`); the function returns the IDs of the overlapping objects as given, unique and ascending. No wrapper.

**B-082.** `cube`: vertices 2 and 3 of every triangle are swapped (`swap_cols`) when `sx * sy * sz < 0`; `plane`:
when `sx * sy < 0` (third element still ignored, normals +z before the rotation). Zero scales stay accepted.
`icosphere`: "Input 'radius' must be a finite positive number." for 0, negative, NaN, Inf. MEX and Python docs of cube
and plane rewritten (they documented the old flip), radius documented in all three.

**B-084.** Pairs are ordered by `(i_obj_1, i_obj_2)` over the sorted unique IDs (key `i_obj_1 * n_obj + i_obj_2`). An
object keeps the smallest key of its overlapping pairs and that pair's finding, the "identical" finding included
(`record` under `omp critical`, keys written with `omp atomic write`). Skip: with `reason`, when both objects already
hold a smaller key; without, when both are flagged (old rule); keys read with `omp atomic read`. `arma::shuffle` is
gone, dynamic scheduling; `new int[n_obj]()` replaced by a `std::vector`. The `arma::mt19937_64_instance` definition is
left for WP-17. D-17: 1 distinct reason vector over 6 calls.

**D13.** The MEX and Python blocks of `ray_triangle_intersect` said that auto mode picks CUDA from 10 000 rays; the
code uses 500; fixed (listed for WP-17, done here because the blocks changed anyway).

  (0-based 0, 3, 11) with the auto (AVX2) and the GENERIC kernel equal the result without sub-clouds; MEX also with
  `point_cloud_segmentation(points, 3)` (vec_size 1).

## Behaviour changes for users

- `icosphere` (C++, MATLAB, Python): the radius must be finite and positive, else `std::invalid_argument` / error
  "Input 'radius' must be a finite positive number." (before: radius 0, NaN and Inf returned NaN coordinates; a
  negative radius threw "cannot be negative").
- `cube` / `plane` (C++, MATLAB, Python) with a negative scale: the winding is swapped when the product of the scales
  (plane: of x and y) is negative, so cube normals stay outward and plane normals +z (as Blender's "Apply Scale");
  before, an odd number of negative scales gave inward / -z normals, and the MATLAB / Python docs said so.
- `subdivide_triangles`, `icosphere`, `cube`, `plane`: an `n_div` whose output count overflows 64 bits throws
  "Input 'n_div' is too large." (before: crash).
- `ray_triangle_intersect` with the AVX2 kernel (the default in AVX2 builds, also MATLAB and Python): hits at the same
  distance (shared edges and vertices) are reported in index order, lowest index as FBS, as with GENERIC. FBS / SBS
  indices (and so materials or objects) change for such rays.
- `ray_triangle_intersect` (both kernels): rays that lie in a plane of a sub-mesh bounding box, e.g. along the bottom
  edge of a wall, are no longer rejected by the box test when they run in z (x and y were already accepted); boundary
  hits can appear where there were none.
- `ray_triangle_intersect<double>` with the AVX2 kernel (default in AVX2 builds; MATLAB and Python always pass double):
  the precision depends on the scene size, not on the distance from the coordinate origin; results at UTM-like
  coordinates are now correct (before: errors of metres at 5e6). Results near the origin change at the float rounding
  level (max |dW| 1.9e-6 for the FBS, 8.3e-6 for the SBS in the benchmark scene). Affects `point_inside_mesh`, `obj_overlap_test`,
  `calc_diffraction_gain` and `path_to_tube`, which call the double version. The AVX2 double path is about 18 % faster;
  with at least n_mesh / 16 rays it uses 24 bytes per triangle of temporary memory.
- `ray_point_intersect` (C++, MATLAB, Python): sub-clouds that are not aligned to 8 (e.g. the default
  `point_cloud_segmentation` output) are accepted with the AVX2 kernel (before: exception in AVX2 builds only).
- `ray_triangle_intersect` (C++): `fbs` / `sbs` may be the same object as `orig` or `dest`; `subdivide_triangles` may
  work in place. Before, both gave wrong results.
- `obj_overlap_test` (C++): an empty mesh returns an empty result (before: crash); overlaps whose penetrating vertices
  lie on extensions of the other object's face planes, or whose edges start on a face, are detected (before: missed);
  the reason strings are deterministic (the finding of each object's first overlapping pair in ID order) and so may
  differ from before; the documentation now says that `obj_ind` holds any IDs (0-based from `obj_file_read`) and that
  the IDs are returned as given.

## Found on the way

- CUDA ray-triangle kernel (`src/ray_triangle_intersect_cuda.cu`, out of scope): the slab fold at lines 226-230 has
  the B-072 pattern (`t_min = (t_min > t2_lo) ? t_min : t2_lo` adopts a NaN of the second or third slab; also the
  -0 direction), and double input is rounded to float coordinates (`RTI_d2f`, B-027 pattern), so its precision for
  double input still depends on the distance from the origin (documented as such). Its tie order is already the
  generic one (FBS through `atomicMin` of the packed (W, face index)), so B-071 does not apply.
- AABB test of the `ray_point_intersect` kernels (note 5): no B-072 pattern. It advances the beam wavefront to the 8
  corners of each sub-cloud box and builds a box with `min_ps` / `max_ps`, which skip a NaN in their first operand;
  there is no per-axis division by the direction. A degenerate beam (vertex direction parallel to the wavefront plane,
  `rD = inf`) could still give 0·inf there.
- `obj_overlap_test`: after a failed `ray_triangle_intersect` inside the OpenMP loop the empty hit vector was
  dereferenced (crash instead of the re-thrown error); guarded in the rewritten lines.

- `icosphere` MEX / Python wrappers compute `20 * n_div * n_div` for the pre-allocation without an overflow check;
