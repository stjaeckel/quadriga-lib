quadriga-lib is a C++ radio channel modelling library with MATLAB / Octave and Python APIs. This document gives the conventions for the Python wrapper (pybind11) of a C++ function: the wrapper in `api_python/`, its registration and its test `tests/python_tests/test_<function_name>.py`. The C++ function, its documentation block and its Catch2 suite exist first (`md/SPEC_CPP_API.md`); the wrapper converts the arguments, allocates outputs and calls it. It should feel natural to Python users and keep the speed of the C++ library.

These conventions are defaults that keep the wrappers consistent, not rules to satisfy at any cost. Prefer the leaner wrapper; where a convention would make it more complex than the case needs, deviate: a deviation inside the wrapper is made and reported in the hand-over with its reason; one that changes the interface users see (names, argument order, defaults, outputs) is proposed first.

# Interface
- The wrapper takes the names and defaults of the C++ declaration, so that users learn one interface for all three APIs; the Glossary in `docs_builder/content/api_intro_cpp.md` applies. Where the wrapper differs (an in/out argument split into `x_in` and `x_out`, another positional order), its documentation block says how and why. Where a MEX wrapper exists, both have the same in/out splits and outputs.
- Keep the wrapper thin: argument conversion, output allocation and the C++ call. Anything that changes results belongs in the C++ library. Releasing the GIL, threads and batch modes are added only after a benchmark shows the need.
- Mandatory arguments are positional; optional ones are keyword-only (`py::kw_only()` in the registration, `*` in the Usage line), except a few that a call almost always passes and that read clearly by position. `tests/python_tests/test_keyword_only.py` records those; changing that list is an interface decision. The positional arguments may be ordered differently from C++ where that reads better.
- Name: the wrapper function has the C++ name; the exposed name drops the prefix that would repeat its submodule (`arrayant_` in `arrayant`, `channel_` and `get_channels_` in `channel`, `sos_` in `sos`, `gbsm_` in `gbsm`, `layout_` in `layout`). The submodule follows the C++ section: antennas, transducers and patterns `arrayant`; channel functions and channel generation `channel`; statistics, math and miscellaneous tools `tools`; site-specific simulation tools `RTtools`; sum-of-sinusoids `sos`; GBSM `gbsm`; network layouts and mobility `layout` (section "Network layouts and mobility").
- Indices stay 0-based; indices documented as 1-based in C++ stay 1-based. Templated C++ functions are called with `double`, fixed-type functions with their type.
- Complex data: one complex array where C++ has an `_re` / `_im` pair, for inputs and outputs; an output is returned as a complex array only. The arrayant dict keeps its split keys and `polmat` its real `(8, n)` form.
- Dicts carry the names of the C++ members as keys. An arrayant is a dict; a multi-frequency arrayant, a `std::vector` of arrayants with one entry per frequency, is one dict whose patterns have the frequency as fourth axis. A `std::vector` of channels is a list of dicts; channel members that hold one entry per snapshot are a list of arrays, or one zero-padded array with the snapshot on the last axis with `stack=True`. Documentation blocks refer to [[generate]] and [[hdf5_read_channel]] for the keys instead of repeating them.
- All outputs are computed and returned; several outputs come as a tuple in the order of the Usage line. A flag that skips outputs or changes the tuple exists only where a measured cost justifies it, and the function documents it. An output that depends on an optional input which was not given is `None`. A new output changes the tuple and breaks existing calls (`a, b = f()`); after 1.0 that is an interface decision. `stack` is the standard flag for a ragged `std::vector` output: a list, or one zero-padded array with the vector index on the last axis.

# Wrapper
- Exemplars: `o2i_loss` in `api_python/qpy_large_scale.cpp` (arrays, a string list, a default, outputs of known size, an integer output) and `interpolate_pattern` in `api_python/qpy_arrayant_interpolate.cpp` (arrayant dict, flags, optional array inputs, zero-copy complex output), registered in `api_python/python_gbsm.cpp` and `api_python/python_arrayant.cpp`. Also: `sos_remove_bias` in `api_python/qpy_sos_val.cpp` (in/out arguments split into `_in` / `_out`, read with `view = false`), `conf_file_read` in `api_python/qpy_conf_file.cpp` (a file reader with dict outputs), `gbsm_single_link_channel` in `api_python/qpy_gbsm_rays.cpp` (a channel dict output with `stack`; its snapshots have equal sizes, so the zero padding is not shown). Their tests are in `tests/python_tests/` under the same names.
- Files: `api_python/qpy_<group>.cpp`, one file per group of functions that belong together, with one documentation section per file. Each submodule has a dispatcher `api_python/python_<submodule>.cpp` (`python_main.cpp` for the top level) that `#include`s its `qpy_*.cpp` files and registers the wrappers with `m.def(...)`; a new file is included there. All wrappers of one submodule form one translation unit, so wrapper and `static` helper names are unique within it.
- Registration: one `py::arg("name")` per parameter in the order of the wrapper signature, with the names of the Usage line. It is the only copy of the Python signature; change it, the wrapper signature and the Usage line together.
- Arguments:
  - Mandatory floating-point arrays are `const py::array_t<dtype> &` with `.none(false)` in the registration; without it `None` is converted into an array. Optional arrays and containers are `py::handle` with default `py::none()`; the helpers turn `None` into an empty object, which means "not given" to C++. An optional C++ input taken by pointer gets `nullptr` for `None`.
  - Flags are `py::handle` read with `qd_python_flag(handle, default, "name")` with the default of the registration; a plain `bool` would turn `None` into `False` and accept any type. File names are `py::handle` read with `qd_python_path(handle, "name")`, which accepts `str`, `bytes` and path-like objects. Other scalars and strings use native types; defaults are set in the registration only.
  - Integer index and count arrays, mandatory ones too (with `.none(false)`), are `py::handle` read with the integer type of the C++ function and the argument name (`qd_python_numpy2arma_Col<arma::uword>(h, true, false, "name")`), so that a negative, fractional or out-of-range entry raises `ValueError`; a `py::array_t` of an integer type would let pybind11 cast such values silently. A native integer scalar rejects them with pybind11's `TypeError`.
- The conversions are in `src/qd_helpers_python.hpp` and, for dicts, flags, file names and `std::any` data, `src/qd_helpers_python_types.hpp`; logic shared with the MEX wrappers (`qd_arrayant_fill_defaults`, `qd_hdf5_select_slots`, ...) is in `src/qd_helpers_wrappers.hpp`; read their comments before writing raw pybind11 or buffer code.
- Traps:
  - `qd_python_copy2numpy`, `stack2numpy` and `copy2list` take their Armadillo inputs by pointer (the string-list overload of `copy2list` takes a reference); the numpy element type is the second template parameter and cannot be deduced: `qd_python_copy2numpy<double, std::complex<double>>(&re, &im)` gives a complex array.
  - `qd_python_init_output` maps a numpy array of fixed size that C++ writes into. Its memory is not zeroed, and its shape must match what C++ produces exactly: another number of elements makes the C++ call fail with "Mat::init(): mismatch between size of auxiliary memory and requested size" (`RuntimeError`), the same number in another shape gives no error and scrambled values; a `std::vector` of cubes that C++ replaces or resizes leaves the returned array unwritten.
  - A copied integer output is cast to signed 64-bit (`qd_python_copy2numpy<arma::uword, py::ssize_t>(&x)`), and the declared return type must match the produced dtype, or pybind11 converts again; a pre-allocated integer output keeps its C++ type.
  - The second argument of `qd_python_numpy2arma_Col`, `_Mat` and `_Cube` is `view`: `true` (as in the exemplars) maps the numpy memory where its layout allows, so the object must not be modified; data that the C++ call changes in place is read with `view = false`.
  - `qd_python_dict2arrayant(dict, view, strict, validate)` has another argument order than the MEX helper. Read with `view = true`, or with `view = false` when the C++ call changes the arrayant in place, so that the user's arrays are not modified.
- An output that grows with the data and whose size the wrapper knows is pre-allocated with `qd_python_init_output`, zero-copy; with an optional `std::complex` output of the C++ function the complex result is zero-copy too. Outputs sized by the call, returned results and small per-element results are copied afterwards.
- pybind11 translates the exceptions: `std::invalid_argument` is `ValueError`, `std::out_of_range` `IndexError`, `std::runtime_error` `RuntimeError`. A wrapper's own check throws `std::invalid_argument`.
- The wrapper is compiled by MSVC for the Windows wheels: the platform rules of `md/SPEC_CPP_API.md`, "Build and platform", apply to it.

# Documentation block
- The rules of the C++ block apply (`md/SPEC_CPP_API.md`, "Documentation block"), with the same one-line summary and the section of the C++ function; do not expand what is brief in C++. A section description (`SECTION_DESC`) of the C++ section has an adapted copy in one wrapper file of the section (e.g. `api_mex/conf_file_read.cpp`, `api_python/qpy_conf_file.cpp`); a change to one goes into the others.
- Differences: the heading is the exposed name (`# <submodule>.<name>` for a name that lost its prefix in `channel`, `sos`, `gbsm` or `layout`, linked the same way; an `arrayant` name keeps the bare heading, e.g. `# generate_antenna`); `## Usage:` replaces the declaration, shows the full call path and the arguments by name only, with `*` before the keyword-only ones, and one line per variant where a flag changes the tuple, with long calls split by continuation lines indented by 4 spaces after a trailing ` \`; Python types and shapes (`(n, m)`, `list`, `dict`, `None`); the dtype only for integer and complex values; optional inputs state `default: X` instead of the *(optional)* mark (kept only where no default can be stated); a C++ return value is listed under `## Outputs:`; no links to functions that exist only in another API.
- `make docs` renders the block into `docs/` (commit it with the change). If the exposed name, read with `.` as `_`, differs from the MATLAB name (a `get_channels_` name without its prefix), add it to `[python_names]` in `docs_builder/content/api_matching.toml`; if the wrapper calls a C++ function of another name, also a second one such as a `_multi` variant (overloads of one name need no entry), add the family to `[families]` (`docs_builder/README.md`, "Cross-language buttons").

# Test
- The test checks the wrapper; the physics is pinned by the Catch2 suite. It shows that inputs reach the right C++ argument, by position and by keyword; outputs come back in their tuple position with the documented type, shape and dtype; optional inputs work omitted, as `None` and given; flags change what they should; inputs are not modified; and that the wrapper's own checks, one C++ error and the pybind11 signature errors raise the specific exception type with a characteristic message. The shared helpers are exercised by many existing tests: one call with another dtype, a list and another memory order is enough, no sweeps.
- Exemplar: `tests/python_tests/test_o2i_loss.py`: one `unittest.TestCase` class `test_case` with one method per aspect, the call through the full path as in the Usage line, small inputs with results that can be written down, `npt.assert_allclose` with explicit `atol` and `rtol` (1e-12 for exact `double` values). Where a test needs them, random inputs come from a seeded `np.random.default_rng` and written files from `tempfile`.
- `make python` builds the module into `lib/`; `python3 -m pytest tests/python_tests/test_<function_name>.py -x -s` runs one file, `make python_test` all of them.

# Hand-over
- The usage line and submodule, the test results as actually run, compiler warnings, and every deviation from the C++ interface or from these conventions, with its reason.
